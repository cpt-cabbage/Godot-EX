### (4) Whether a 6DOF angular spring with zero damping counts as active under Jolt (pass-one gap, now answered from source)

- In `Position` mode Jolt activates the rotation motor part only if `spring_settings.HasStiffness()`; otherwise it calls `Deactivate()` (no drive at all) — `thirdparty/jolt_physics/Jolt/Physics/Constraints/SixDOFConstraint.cpp:571-577` (translation: `:430-437`). `HasStiffness()` is `mFrequency > 0.0f` (`SpringSettings.h:41`) and `mStiffness` aliases `mFrequency` in the union (`:52-57`), so in `StiffnessAndDamping` mode **stiffness > 0 is required and damping may be 0**. In `PositionAndVelocity` mode the test is `HasStiffnessOrDamping()` (`SixDOFConstraint.cpp:581-587`; `SpringSettings.h:44`), so a damping-only drive (pure velocity tracking) is legal. `SpringPart.h:38` asserts `inStiffness > 0.0f || inDamping > 0.0f`. This closes the milestone-one check "whether the spring counts as active with zero damping": it does, provided stiffness is non-zero; a zero-stiffness spring silently does nothing rather than acting as a hard drive.

## 4. Contradictions found in the report (and pass-one note)

1. **Wrong method name.** Report ("What the fork exposes", line 17) and pass one list the node API as `has_angular_target_rotation`; the bound method is `has_target_rotation()` (`scene/3d/physics/joints/generic_6dof_joint_3d.cpp:58`, `generic_6dof_joint_3d.h:123`, `doc/classes/Generic6DOFJoint3D.xml:61`). The server has no `has_*` at all; use `PhysicsServer3D.generic_6dof_joint_get_angular_target_rotation()` (identity when unset).
2. **Two PRs, not one.** The report attributes both the quaternion target and the drive limits to "the June 2026 addition" / PR #118997. The quaternion target is [PR #118997](https://github.com/godotengine/godot/pull/118997) (merged 2026-06-23); `PARAM_LINEAR_DRIVE_FORCE_LIMIT`/`PARAM_ANGULAR_DRIVE_TORQUE_LIMIT` and the deprecations are [PR #119332](https://github.com/godotengine/godot/pull/119332) (nikolay-egorov, opened 2026-05-08, merged 2026-06-26, closing proposal #14745). Both are milestone 4.8; the bibliography should list both.
3. **Phase 0 item already upstream.** "Expose `get_applied_force/get_applied_torque` on joints" (report lines 53, 226) is being merged upstream as [PR #123875](https://github.com/godotengine/godot/pull/123875) (approved by jrouwe 2026-09-27). Cherry-pick it rather than writing a fork-local binding, to avoid a later merge conflict on `Joint3D`/`PhysicsServer3D` bindings.
4. **6DOF angular limits are a pyramid, not a cone.** The report proposes "cone-type limits at shoulders, hips and neck … all implemented as 6DOF joints with angular limits" (line 25). Jolt's 6DOF wrapper hard-codes `constraint_settings.mSwingType = JPH::ESwingType::Pyramid` (`modules/jolt_physics/joints/jolt_generic_6dof_joint_3d.cpp:80`), whereas `ConeTwistJoint3D` now uses Jolt's default `ESwingType::Cone` after PR #119982 (fixing issue #119926, where Jolt "appears to extend joint freedom into the corners of a pyramid"). A pyramid lets the limb reach the swing-space corners a true cone forbids. Either accept it, or add a one-line Phase 0 option (Jolt-only flag) to select `ESwingType::Cone` on 6DOF joints, or use `ConeTwistJoint3D` plus a Phase 0 `Position` motor patch (which the report already lists) for shoulders and hips.
5. **Quaternion target is cleared by the equilibrium parameter.** The report says PhysicalBone3D's joint "already stores … `angular_equilibrium_point` … the target must be supplied each tick by script through `get_joint_rid()`" (line 25). True, with the added constraint that any write of `G6DOF_JOINT_ANGULAR_SPRING_EQUILIBRIUM_POINT` clears the quaternion target in both node and module (`generic_6dof_joint_3d.cpp:228-230`; `jolt_generic_6dof_joint_3d.cpp:464-468`), and PhysicalBone3D re-writes that parameter in `_reload_joint()` (`physical_bone_3d.cpp:1036`), which runs on tree entry, joint-type change and bone-parent change (`:757-767, 1044-1046, 1124`). Setting the target every physics tick (as the design does) hides this, but a one-shot "set target then let the spring hold" pattern would silently revert to the Euler equilibrium.
6. **Zero-damping question answered, zero-stiffness is the real trap.** Milestone one asks to "check whether the spring counts as active with zero damping" (line 226). Source answer: in `Position` mode Jolt deactivates the motor part unless stiffness > 0 (`SixDOFConstraint.cpp:571-577`; `SpringSettings.h:41`); damping may be zero. The default `angular_spring_*/stiffness` of PhysicalBone3D's 6DOF data is 0.0 (`physical_bone_3d.h:155`), so a spring enabled with default stiffness drives nothing.
7. **The (prevPose, pose, dt) emulation now has a code path, but it is four weeks old.** Pass one's inference that feeding the animation's angular velocity through `angular_motor_*/target_velocity` alongside the spring emulates `DriveToPoseUsingMotors(prev, pose, dt)` is supported by upstream PR #122996 (2026-08-31) which maps motor+spring to `PositionAndVelocity` (`jolt_generic_6dof_joint_3d.cpp:114-115`). Caveats: the motor target angular velocity is expressed in the constraint space of body 2 (`SixDOFConstraint.h:179-181`) with the module's per-axis sign flip (`:137-141`), and it remains untested at runtime in this fork.
8. **Hinge conversion lines.** Report and pass one cite `jolt_hinge_joint_3d.cpp:195-197,235-238`; the two conversions are at `:195-196` and `:239-240`.
9. **"Physics interpolation on" needs a caveat for the skinned mesh.** Since PR #119509 (in this fork: `bone_attachment_3d.cpp:375`, `spring_bone_collision_3d.cpp:210`), bone-following nodes force interpolation OFF and warn, because skeleton children are moved by deferred processing. The report's rig writes simulated poses into the `Skeleton3D` via `set_bone_global_pose` (`physical_bone_3d.cpp:833`); skeleton bone poses are not `Node3D` transforms and the docs say 3D interpolation "is implemented on the scene side", so the skinned `MeshInstance3D` is expected to step at tick rate regardless of the project setting, while the top-level `PhysicalBone3D` nodes themselves are interpolated. At 120 Hz this is likely invisible; at 60 Hz it is not. Inference from source and docs, unverified at runtime; add it to the milestone-one checks.
10. **Profiling advice.** "Profile with the 'Physics Process' monitor and Jolt's body-pair counters" (line 41): Jolt's `Performance` counters are stubbed to 0 (`jolt_physics_server_3d.cpp:1687-1689`; [issue #123514](https://github.com/godotengine/godot/issues/123514)). Only the time monitor works.
11. **ONNX status is stale.** "the native ONNX GDExtension is unmaintained since February 2024" (line 218): mat490's loader was updated 2026-06-16 and its MIT fork godot-onnx-loader (Godot 4.6+, ONNX Runtime 1.20.1) on 2026-09-26; godot-infer adds GPU compute-shader inference for 4.5+ (Section 2 (3)). The report's conclusion (a small custom MLP or ncnn via godot-native-rl remains the lightest route) still stands, but the premise should be corrected.
12. **Pass-one Ragdoll grep.** "`grep -rn Ragdoll modules/jolt_physics` finds nothing" is wrong in the letter (SCsub:116 matches) though right in substance (compiled, not wrapped).
13. **Pass-one PositionAndVelocity attribution.** Pass one presents the motor-state mapping as settled behaviour; it should be marked as upstream PR #122996 (2026-08-31), since anyone on 4.7 or earlier gets `Velocity` only when both flags are on.
14. **Flag naming for implementers.** Neither document names the motor flag; new code should use `FLAG_ENABLE_ANGULAR_MOTOR` / `G6DOF_JOINT_FLAG_ENABLE_ANGULAR_MOTOR` (PR #96458); `FLAG_ENABLE_MOTOR` is a deprecated alias (`doc/classes/Generic6DOFJoint3D.xml:460`).
15. **Report bibliography completeness.** The "Local fork files verified" list (report lines 618-648) omits files the text relies on: `scene/3d/physics/joints/generic_6dof_joint_3d.h`, `modules/jolt_physics/joints/jolt_cone_twist_joint_3d.cpp`, `jolt_hinge_joint_3d.cpp`, `jolt_joint_3d.cpp`, `modules/godot_physics_3d/godot_physics_server_3d.cpp`, `servers/physics_3d/physics_server_3d_extension.cpp/.h`, `physics_server_3d_wrap_mt.h`, `scene/3d/skeleton_modifier_3d.h`, `scene/3d/physics/physical_bone_simulator_3d.cpp/.h`, `doc/classes/SkeletonModifier3D.xml`, `doc/classes/PhysicalBone3D.xml`, `doc/classes/Engine.xml`, `thirdparty/jolt_physics/Jolt/Physics/Ragdoll/Ragdoll.cpp`, `.../Constraints/SixDOFConstraint.cpp`, `.../PhysicsSystem.h`, `.../PhysicsSettings.h`, `.../Character/CharacterVirtual.h`.

Everything else checked in the report's engine sections (single-step `Update`, no sub-stepping knob, 60-tick default and `max_physics_steps_per_frame` guidance, Jolt default solver iterations and sleep thresholds, `continuous_cd` → `LinearCast`, 500 m/s velocity cap, `custom_integrator` semantics, non-allocating queries from PR #113970, the `AnimationMixer`/`Skeleton3D` PHYSICS callback modes, the `SetTargetOrientationBS` body-space formula and the `q = basis_A⁻¹ · basis_B_desired` usage, CharacterVirtual's defaults) holds against the tree.
