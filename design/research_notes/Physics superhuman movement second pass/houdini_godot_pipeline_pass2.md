## 2. Gaps closed

### 2.1 Configure Joints dictionary keys (from the `solvephysfbik` VEX page)
Source: [solvephysfbik — Houdini VEX functions, SideFX docs, 2026](https://www.sidefx.com/docs/houdini/vex/functions/solvephysfbik.html). Signature: `matrix[] solvephysfbik(matrix xforms[], int parents[], dict jointoptions[], matrix targetxforms[], int targets[], dict targetoptions[], int iters, float damping, float tolerance)`. The `jointoptions` dictionary (what Configure Joints writes per point) accepts:

| Key | Type | Default | Meaning (verbatim where quoted) |
|---|---|---|---|
| `rotation_weights` | vector | `{1,1,1}` | "weights for the joint's rotation axes … A weight of zero will disable the rotation axis." |
| `translation_weights` | vector | `{0,0,0}` | "A weight of zero will disable the translation axis. To achieve an unpinned root joint, the root's translation weight should be non-zero" |
| `rotation_order` | int | XYZ | `XFORM_XYZ` etc.; in Ragdoll mode this is what fixes the twist (first) and up (second) axes for the cone-twist constraint ([Configure Joints docs](https://www.sidefx.com/docs/houdini/nodes/sop/kinefx--configurejoints.html)) |
| `rotation_lower_limits` / `rotation_upper_limits` | vector | `{0,0,0}` | "Lower rotation limits (in radians) for the joint's rotation axes, applied relative to rest transform if specified." |
| `translation_lower_limits` / `translation_upper_limits` | vector | `{0,0,0}` | translation limits per axis |
| `rest_xform` | matrix | identity | "Local space matrix specifying the joint's rest pose." |
| `rest_rotation_weights` / `rest_translation_weights` | vector | `{0,0,0}` | "How strongly the solver attempts to match the rest transform … A value of 0.1 is typically suitable when enabled." |
| `mass` | float | 1.0 | "Mass of the body associated with the joint. Only used when a center of mass target is provided." |
| `local_com` | vector | `{0,0,0}` | "Position of the joint's center of mass, in local space." |

Implication for the Godot mapping in the report: the limits arrive as three lower/upper angle pairs in radians in the joint's rotation-order frame, not as an explicit swing/twist pair; a post-import script derives cone (swing span = upper−lower on the two non-twist axes) and twist span from `rotation_order`, and can use `mass`/`local_com` for `PhysicalBone3D.mass` and shape offsets.

### 2.2 Does ROP GLTF Character Output export extras or custom attributes? No.
The full parameter list ([ROP GLTF Character Output SOP — SideFX docs](https://www.sidefx.com/docs/houdini/nodes/sop/kinefx--rop_gltfcharacteroutput.html)) is: Clip Range (Use clipinfo Detail Attribute / Render Current Frame / Frame Range / Strict / Start-End-Inc), Render with Take, Image Format (Original or PNG, Original or JPEG, PNG, JPEG), Additional Textures (Texture Name, Texture Image Path), Animated Pose Export (Single Clip / Multiple Clips), Clip Name Attribute, Clip Name, Copyright, Export Materials, Export Skin Mesh Name, Mesh Name Source, Export Joint Names, and the five script hooks (Pre-Render, Pre-Frame, Post-Frame, Post-Write, Post-Render). Three routes remain: (a) a JSON sidecar written from hython; (b) a Post-Write Script that opens the emitted `.gltf` text and injects `extras` onto joint nodes (the generic glTF ROP 2.0's `gltf_node_extras` cannot help because that ROP does not write skins, [glTF ROP 22.0 docs](https://www.sidefx.com/docs/houdini/nodes/out/gltf.html)); (c) name-encoding on joints. On the Godot side, extras on joint nodes are preserved as bone metadata (`skin_tool.cpp` 640–642, local tree; [PR #86183](https://github.com/godotengine/godot/pull/86183)), so route (b) yields `Skeleton3D.get_bone_meta(bone, "extras")` directly.

### 2.4 Glue strength and impulses
- [Glue Constraint Relationship DOP — SideFX docs, 2026](https://www.sidefx.com/docs/houdini/nodes/dop/glueconrel.html): "Whenever a glued object gets hit, it accumulates a glue impulse force. This controls how fast that force decays." (Half-Life); "Glue constraints can only be broken by things colliding with them, generating an impact."; Propagation Rate: "Specifies how impulses from collisions spread across the Constraint Network" with a weighted average and self-rate 1; Propagation Iterations: "Impulses will not travel more than this number of bonds each solve step."
- [Constraint networks — Houdini destruction docs, SideFX, 2026](https://www.sidefx.com/docs/houdini/destruction/constraints.html): "Each constraint is represented by a two-point polyline"; endpoints carry `name`; glue constraints "keep two pieces together until the amount of force trying to separate them is greater than the glue strength"; soft constraints "bend until they break".
- [Bullet Solver DOP — SideFX docs, 2026](https://www.sidefx.com/docs/houdini/nodes/dop/bulletrbdsolver.html) and [RBD Constraint Properties](https://www.sidefx.com/docs/houdini/nodes/sop/rbdconstraintproperties.html) give **no units** for `strength` or impulse.
- Inference (not documented): `strength` is compared against an accumulated, decaying, network-propagated collision impulse in the scene's mass×velocity units; only ordering and ratios are portable. A Godot/Jolt runtime should treat `strength` as a relative threshold to be recalibrated against its own contact impulses, and should reimplement decay (`half_life`) and propagation (`propagation_rate`, `propagate_iteration`) if it wants Houdini-like behaviour.

The technical claim is now false; the licensing claim stands (HAPI checks out an Engine/Core/FX/Engine Indie/Indie licence on the running machine, [HAPI Licensing](https://www.sidefx.com/docs/hengine/_h_a_p_i__licensing.html)). Reword to a licensing argument only.
3. **HEGo README quotation is not verbatim.** The README reads "No license needed for building, active commercial(FX,Core or Houdini Engine) license required for runtime" ([HEGo README raw](https://raw.githubusercontent.com/peterprickarz/hego/main/README.md)); the report presents a smoothed sentence inside quotation marks.
4. **Draco citation.** Issue #73738 is closed/archived (opened 2023-02-22, Godot 3.5.1/4.0.rc2) ([issue #73738](https://github.com/godotengine/godot/issues/73738)); the report cites it as the evidence that Godot "refuses" Draco. The durable evidence is the fork's `supported_extensions` list (local `gltf_document.cpp` 7011–7018), which should be cited instead.
5. **"-convcolonly for V-HACD convex decomposition."** The Godot docs say only "convex decomposition" ([node type customization](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/node_type_customization.html)); V-HACD is confirmed by the local importer source (`resource_importer_scene.cpp` 480, `thirdparty/vhacd`), not by the cited page. Cite the tree.
6. **HTerrain claim.** "Terrain3D and HTerrain both import ('Only use 16 or 32-bit height data')" attributes a Terrain3D sentence to both; HTerrain's docs name RAW 16/32-bit and PNG 8-bit, EXR is supported only in code, and the plugin is in bug-fix-only maintenance on Godot 4.6+ ([HTerrain docs](https://hterrain-plugin.readthedocs.io/en/latest/); [hterrain_data.gd](https://raw.githubusercontent.com/Zylann/godot_heightmap_plugin/master/addons/zylann.hterrain/hterrain_data.gd); [README](https://raw.githubusercontent.com/Zylann/godot_heightmap_plugin/master/README.md)). Terrain3D 1.0.2 is documented for Godot 4.4–4.6 only ([Terrain3D installation](https://terrain3d.readthedocs.io/en/stable/docs/installation.html)); neither is verified on 4.8-dev.
7. **Godot_VAT3 "uncompressed 16/32-bit EXR textures".** The README requires uncompressed textures and glTF export but does not name EXR ([Godot_VAT3 README](https://raw.githubusercontent.com/G4ND44/Godot_VAT3/main/README.md)); EXR is one of four VAT output formats ([Labs VAT 3.0](https://www.sidefx.com/docs/houdini/nodes/out/labs--vertex_animation_textures-3.0.html)). Also unflagged: the port's HDA is `.hdalc` (limited-commercial), so on a commercial Houdini seat it would taint the session ([Houdini Indie page](https://www.sidefx.com/products/houdini-indie/); [HAPI Licensing tainting rule](https://www.sidefx.com/docs/hengine/_h_a_p_i__licensing.html)) — fine for Indie, a nuisance for FX/Core.
8. **RBD Material Fracture "Metal" and the docs page.** Metal bending/tearing is new in Houdini 22 ([H22 RBD notes](https://www.sidefx.com/docs/houdini/news/22/rbd.html)); the report presents the five material types without a version.
9. **Constraint types list.** The report lists `constraint_type` values "glue, hard, soft, cone twist, slider, spring"; this pass's re-read of the RBD Constraint Properties page surfaced only glue, hard and soft with their attribute names. The other three are not contradicted (pass one read them from the same page) but were not re-verified here.
10. **Ragdoll mapping detail.** The report says Configure Joints "stores per-joint angle ranges and twist/up axes in a dictionary attribute". Precisely: it stores `rotation_lower_limits`/`rotation_upper_limits` (radians) and `rotation_order`; the twist/up axes are implied by the rotation order rather than stored as separate keys ([solvephysfbik](https://www.sidefx.com/docs/houdini/vex/functions/solvephysfbik.html); [Configure Joints](https://www.sidefx.com/docs/houdini/nodes/sop/kinefx--configurejoints.html)).
11. **Unstated but supportive:** the report's plan to carry ragdoll limits as glTF extras on joints is now backed by the fork's bone-metadata path (`skin_tool.cpp` 640–642), and the Ragdoll Solver's engine is Bullet ([Ragdoll Solver 2.0](https://www.sidefx.com/docs/houdini/nodes/sop/kinefx--ragdollsolver.html)), consistent with the report's remark that its CFM/ERP-style parameters do not transfer to Jolt.
