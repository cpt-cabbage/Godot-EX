# Houdini to Godot 4 pipeline for a physics-heavy game (Jolt physics)

Research date: 2026-09-27. Scope: whether Houdini Engine exists for Godot, and a sourced catalogue of what Houdini can author offline for a Godot 4.x (4.8-dev fork, Jolt) project: destruction, procedural environments, character rigs/ragdolls, physics authoring. Every finding carries a citation; anything I could not verify is listed under Gaps rather than asserted.

Source-access note: github.com pages opened fine through WebFetch in this session; the GitHub MCP repository-search endpoint returned a 502 once and was not retried (all GitHub facts below come from fetched repo/issue pages instead). Two SideFX doc URLs I guessed (`kinefx--rbdconfigureragdoll.html`, `solidconform.html`, `kinefx--ragdollsolver-2.0.html`) returned 404; I used the correct pages found via search (`kinefx--ragdollsolver.html`, `tetconform.html`, `character/kinefx/ragdoll.html`). ## Key question 1: Does Houdini Engine exist for Godot (official or community), and what does licensing cost?

### Takeaway
SideFX ships no official Houdini Engine plugin for Godot (official hosts are Unreal, Unity, Maya, 3ds Max, plus a Maxon-maintained Cinema 4D plugin). A community C++ GDExtension, **HEGo** by Peter Prickarz (MIT, Godot 4.4+, Houdini 22.0.429+, Windows/Linux), exists and is actively maintained through 2026, but it can only run with a *commercial* Houdini/Houdini Engine license because SideFX's Houdini Engine Indie only works with the official plugins and custom HAPI integrations require a commercial Houdini Engine license (USD 525/yr workstation, from USD 795/yr floating). For an indie-budget team the practical route is therefore offline export (glTF/FBX/heightmap textures), which needs only Houdini (Indie: USD 299/yr) and no Engine license.

### Inferences
- For this project (indie budget implied by the brief), live Houdini Engine in Godot is a commercial-license-only path (~USD 525/yr Engine Workstation on top of a Houdini seat, or a Core/FX seat). HEGo is the only integration found; it is young (0.x), Windows/Linux only, and its own README ties runtime to a commercial license. Unless SideFX changes the Indie policy (the author says talks are ongoing, unconfirmed by SideFX), plan on **offline export**, for which Houdini Indie (USD 299/yr) suffices and no Engine license is needed.
- Because HEGo runs Houdini cooks off the main thread and bridges to Terrain3D, it is worth evaluating as an *editor-time* tool (level authoring, terrain), never as a shipped runtime dependency: shipped builds would need a Houdini Engine license on every machine, which the FAQ's licensing model does not contemplate for end users.
- houdini2godot (TSCN/ESCN + glTF, Godot instancers) is the closest thing to a "Godot ROP"; it is a one-person project and has not been verified against Godot 4.8-dev.

### Gaps
- I could not find any SideFX statement (product page, FAQ, forum) about planned Godot support or about allowing Indie use of third-party plugins; only the HEGo author's second-hand claim exists.
- Exact HEGo release years could not be confirmed from the releases page rendering (see caveat above).
- houdini2godot's last-commit date and Godot 4.4+/4.8 compatibility were not visible in the fetched README.
- Whether HEGo compiles against a Godot 4.8-dev fork (godot-cpp version pinning) was not documented.

## Key question 2: SideFX Labs and export tools relevant to Godot (glTF ROP, FBX, VAT, Labs tools, PDG, hython) and how Godot 4 imports glTF (import hints)

### Takeaway
Houdini's generic glTF ROP exports hierarchies, materials, transform animations, lights, Draco and custom attributes/extras but **not skinning or morph targets**; skinned characters go through the KineFX "ROP GLTF Character Output" SOP (H19+) or the FBX character ROPs. Godot 4 recommends glTF, applies node-name suffixes (`-col`, `-convcol`, `-colonly`, `-convcolonly`, `-rigid`, `-vehicle`, `-wheel`, `-navmesh`, `-occ`, `-occonly`, `-noimp`, `-loop`/`-cycle`, `-alpha`, `-vcol`) at import, and since 4.4 imports glTF `extras` into node/mesh/material metadata; it does not import Draco-compressed glTF and does not turn EXT_mesh_gpu_instancing into MultiMeshInstance3D. Labs VAT 3.0 ships shaders only for Unreal/Unity, but a community MIT Godot port (Godot_VAT3) exists. No Labs tool targets Godot.

### Cited Findings
**Houdini glTF export**
- The Houdini glTF 2.0 ROP supports scenes, nodes, meshes and mesh primitives (points, lines, triangles), cameras, materials (Principled Shader, MtlX glTF material), textures and custom attributes, transform animations (single or multiple clips), lights via KHR_lights_punctual, Draco compression (triangles only); **unsupported**: skinning/skeletal deformation, morph targets, animation weight targets. Output ".glb" (single binary) or ".gltf" (text plus external resources). Key parameters: "Use SOP Path"/"SOP Path", "Build Hierarchy from Path Attribute" (create nodes from a primitive string attribute), "Export Materials", "Image Export", "Export Animations to" (Single Clip / Multiple Clips / None), "Use Draco Compression", "Export Custom Attributes" (underscore-prefixed attributes; must be point-level, others need promotion), "Export Extras" ("include dictionary attributes as glTF properties"), "Export Cameras", "Export Lights"; pre/post-render and post-write script hooks in HScript or Python — [glTF ROP docs — SideFX, accessed 2026](https://www.sidefx.com/docs/houdini/nodes/out/gltf.html)
- The ROP GLTF Character Output SOP exports "a skinned character with a geometry-based skeleton to a glTF or glb (binary) file"; inputs Rest Geometry (skin with `boneCapture` point attribute and `name`/`path` primitive attribute), Capture Pose and Animated Pose (skeleton points with `P`, `transform`, `name`, hierarchy as two-point polygons); exports glTF skin from `boneCapture`, joints as nodes, transform and weight-target animation, morph targets, Principled Shader materials and textures; parameters "Animated Pose Export" (Single Clip / Multiple Clips), "Clip Name Attribute", "Image Format", "Export Materials", "Export Skin Mesh Name", "Export Joint Names"; not supported: point/line primitives, cameras, Draco, KHR_lights_punctual; introduced in Houdini 19.0 — [ROP GLTF Character Output SOP docs — SideFX, accessed 2026](https://www.sidefx.com/docs/houdini/nodes/sop/kinefx--rop_gltfcharacteroutput.html)
- KineFX export options: ROP FBX Animation Output SOP ("Export animation from geometry-based skeleton to an FBX file"), ROP FBX Character Output SOP ("Export a skinned character with geometry-based skeleton to an FBX file"), ROP GLTF Character Output SOP (glTF/glb, "ideal for Web, Mobile, or AR/VR"), File SOP for native formats, SOP Import UsdSkel Character LOP for Solaris; Alembic is not mentioned — [Getting animation and character data out of KineFX — SideFX docs, accessed 2026](https://www.sidefx.com/docs/houdini/character/kinefx/exportcharacters.html)
- The Filmbox FBX ROP exports skinning/deformation, skeletons, animation and blendshapes; parameters "Export Deforms as Vertex Caches", "Force Skin Deform Export" (only Bone Deform, Bone Capture and Capture Override supported), "Export End Effectors", "Export in ASCII", "FBX SDK Version", "Vertex Cache Format" (MC or PC2), "Force Blend Shape Export", "Detect Constant Point Count Dynamic Objects"; particle systems/fluids with changing topology cannot be exported as such — [Filmbox FBX ROP docs — SideFX, accessed 2026](https://www.sidefx.com/docs/houdini/nodes/out/filmboxfbx.html)

**Godot 4 import side**
- Godot 4 imports glTF 2.0 (.gltf/.glb, "recommended"), .blend, FBX (via ufbx or FBX2glTF), DAE and OBJ; OBJ "doesn't support skinning, animation, UV2 or PBR materials" — [Available 3D formats — Godot docs (stable), accessed 2026](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html)
- Godot import hints by node-name suffix (separators `-`, `$` or `_`, case-insensitive): `-noimp` removes the node/animation; `-col` creates a static collision child with a triangle-mesh (concave) shape and keeps the mesh; `-convcol` creates "ConvexPolygonShape3D instead of a ConcavePolygonShape3D"; `-colonly` "will remove the mesh upon importing and will create a StaticBody3D collision instead"; `-convcolonly` same but "will create a ConvexPolygonShape3D instead using convex decomposition"; `-occ` creates an Occluder3D and keeps the mesh; `-occonly` converts to Occluder3D; `-navmesh` converts to a navigation mesh and removes the mesh; `-rigid` "will be imported as a RigidBody3D"; `-vehicle` "as a child to a VehicleBody3D node"; `-wheel` "as a child to a VehicleWheel3D node"; `-loop`/`-cycle` sets the animation loop flag; `-alpha` sets TRANSPARENCY_ALPHA; `-vcol` sets vertex-colour flags — [Node type customization using name suffixes — Godot docs (stable), accessed 2026](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/node_type_customization.html)
- Godot PR #86183 "Import/export GLTF extras to node->meta and back" (author demolke) was merged 30 Aug 2024 for milestone 4.4; it propagates parsed glTF extras into Node metadata as an `extras` dictionary for nodes, meshes and materials, and exports metadata back — [godotengine/godot PR 86183 — demolke, 2024](https://github.com/godotengine/godot/pull/86183); proposal #8271 "Import custom glTF properties as node metadata" is closed as implemented — [godot-proposals #8271, 2023–2024](https://github.com/godotengine/godot-proposals/issues/8271); a Godot 4.4-stable user confirms `mesh.get_meta("extras")` returns Blender custom properties — [GLTf Import: How does one get Metadata/Extras? — Godot Forum, 2025](https://forum.godotengine.org/t/gltf-import-how-does-one-get-metadata-extras/105711)
- Post-import automation: a script extending `EditorScenePostImport` with `_post_import(scene)` (must be `@tool`) is set under Import dock "Import Script" > "Path" and can rewrite the imported scene — [Import configuration — Godot docs (stable), accessed 2026](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/import_configuration.html)
- Godot `GLTFLight` "Represents a light as defined by the KHR_lights_punctual glTF extension"; types point (OmniLight3D), spot (SpotLight3D), directional (DirectionalLight3D) — [GLTFLight class — Godot docs (stable), accessed 2026](https://docs.godotengine.org/en/stable/classes/class_gltflight.html)
- Godot refuses Draco-compressed glTF: "GLTF: Can't import file, required extension 'KHR_draco_mesh_compression' is not supported" (reported through 4.3, Dec 2024); a proposal asks for GLTFDocument hooks so Draco could be added via GDExtension — [godotengine/godot issue #73738](https://github.com/godotengine/godot/issues/73738); [godot-proposals #8576](https://github.com/godotengine/godot-proposals/issues/8576); [Godot Forum: Compression version of GLB/GLTF is not working, 2024](https://forum.godotengine.org/t/compression-version-of-glb-gltf-is-not-working/94486)
- EXT_mesh_gpu_instancing is not picked up: proposal #8787 "Automatically pick up EXT_mesh_gpu_instancing gltf extension" (opened 3 Jan 2024) is still open — [godot-proposals #8787, 2024](https://github.com/godotengine/godot-proposals/issues/8787); issue #109280 (opened 3 Aug 2025, Godot 4.5.beta4) reports that a Blender glTF with GPU instances imports as "a separate mesh for every object" rather than one MultiMeshInstance3D; open, no maintainer reply visible — [godotengine/godot issue #109280, 2025](https://github.com/godotengine/godot/issues/109280)

### Inferences
- The clean Houdini-to-Godot contract is: emit `.glb` from the glTF ROP with **Draco off**, name nodes with Godot suffixes via Houdini's `path`/`name` attributes (using "Build Hierarchy from Path Attribute"), and pack any per-object data (piece IDs, constraint tables, material tags) into dictionary attributes exported through "Export Extras" so Godot 4.4+ lands them in `get_meta("extras")` for an `EditorScenePostImport` script.
- Skinned characters need the KineFX glTF Character Output SOP (or FBX character ROP), not the generic ROP.
- VAT for Godot is feasible via Godot_VAT3 (community, unversioned) with exported 16/32-bit EXR textures; expect to maintain the shader yourself on a 4.8-dev fork.
- Instanced scatter (trees, rubble) cannot rely on EXT_mesh_gpu_instancing; either emit point data (e.g. JSON/extras) and build MultiMesh in a post-import script, or use houdini2godot's instancer output.

### Gaps
- I could not open the "Export Extras" parameter's exact accepted attribute classes (point/prim/detail) beyond the summary; verify on the ROP page.
- No official documentation was found for VAT precision requirements in Godot's importer (e.g. whether Godot keeps 32-bit EXR as RGBAF textures at import); Godot_VAT3's README only says "no compression".
- Whether Houdini Indie restricts glTF/FBX export in any way: the Indie page mentions only its own scene/asset file format and renderer list; I found no statement either way about export formats.

## Key question 3: Destruction authoring (RBD Material Fracture, constraint networks, export of piece meshes plus constraint graph, RBD Bullet Solver bakes vs runtime, pre-baked VAT destruction, convex decomposition)

### Takeaway
Houdini's RBD Material Fracture produces per-material pieces (Concrete/Glass/Wood/Metal/Custom) plus a **constraint network as polyline primitives between piece centroids** and optional convex-decomposed proxy geometry; RBD Constraint Properties writes the attributes (`constraint_name`, `constraint_type`, `strength` with -1 = unbreakable, `half_life`, `propagation_rate`, soft/hard params) that a Blast/RealBlast-style support graph needs. Nothing exports that graph natively for Godot, but the data is plain point/primitive attributes readable in Python/hython or emitted as glTF extras/custom attributes. Bullet bakes are for offline VAT/alembic-style playback; runtime pieces should be exported as static geometry with convex proxies (Houdini's Convex Decomposition SOP or Godot's V-HACD "Create Multiple Convex Collision Siblings"/`-convcolonly`).

### Cited Findings
- RBD Material Fracture supports five material types — Concrete, Glass (Flat Panes or Curved Glass), Wood, Custom and Metal — and outputs three streams: fractured geometry, constraint geometry ("polyline primitives representing connections between fractured pieces", connecting piece centroids), and proxy geometry (convex decomposition, packed spheres or thickening). It writes `name` per piece (with "Piece Prefix"), optional `constraint_tag`, `creaseweights`, `fracture_ID`; constraint strength parameters include Primary/Radial/Concentric/Chipping Strength and Strength Variance; a "Soft Constraint Name" lets broken glue switch to a soft constraint — [RBD Material Fracture SOP docs — SideFX, accessed 2026](https://www.sidefx.com/docs/houdini/nodes/sop/rbdmaterialfracture.html)
- RBD Constraint Properties supports constraint types glue, hard, soft, cone twist, slider, spring and writes primitive attributes: `constraint_name`, `constraint_type`, `conedof`, `disable_collisions`; glue: `strength` ("If the value is -1, the connection will never break"), `strength_variance`, `half_life`, `propagation_rate` (0–1), `propagate_iteration`; hard: `cfm`, `erp`, `numangularmotors`, `axis1`, `axis2`, `targetw`, `maxangularimpulse`; soft: `stiffness`, `damping_ratio`, `angular_stiffness`, `angular_damping_ratio`, `plasticity_rate`, `plasticity_threshold`, `plasticity_hardening`; strength has no stated units — [RBD Constraint Properties SOP docs — SideFX, accessed 2026](https://www.sidefx.com/docs/houdini/nodes/sop/rbdconstraintproperties.html)
- The RBD Bullet Solver SOP "Runs a dynamic Bullet simulation" with inputs render geometry, constraint geometry, proxy geometry, collision geometry and guide geometry; reads per-piece `density`, `velocity`, `active`, `bounce`, `friction`, `rotational_stiffness`, `animated`, `accelmax`, `speedmin`, `speedmax`; constraint geometry needs `name` point attributes matching pieces and `constraint_name` primitive attributes, plus `strength`, `restlength`, glue properties; outputs transformed geometry per frame and a primitive group `broken` of constraints broken by the solver — [RBD Bullet Solver SOP docs — SideFX, accessed 2026](https://www.sidefx.com/docs/houdini/nodes/sop/rbdbulletsolver.html)
- Houdini's Convex Decomposition SOP is intended for rigid body dynamics; its main control is "Max Concavity" ("The maximum distance from a point on the geometry to it's closest convex hull edge"); options "Treat as Solid", "Merge Nearby Segments", "Use Piece Attribute" (decompose each fractured piece separately), output either segmented geometry (with "Segment Attribute") or the convex hulls; the docs do not name the algorithm; PolyReduce on hulls "may help with performance for simulations with Bullet" — [Convex Decomposition SOP docs — SideFX, accessed 2026](https://www.sidefx.com/docs/houdini/nodes/sop/convexdecomposition.html)
- Godot: "Create Single Convex Collision Sibling" uses Quickhull, "Create Multiple Convex Collision Siblings" "uses the V-HACD algorithm" giving "more accuracy for concave objects at the cost of performance"; docs "recommend favoring primitive shapes for dynamic objects such as RigidBodies and CharacterBodies"; multiple convex shapes can beat one concave shape "though this performance advantage no longer applies after a certain amount of convex shapes" — [Collision shapes (3D) — Godot docs (stable), accessed 2026](https://docs.godotengine.org/en/stable/tutorials/physics/collision_shapes_3d.html)
- Godot's `-convcolonly` suffix "will create a ConvexPolygonShape3D instead using convex decomposition"; `-rigid` imports a node as RigidBody3D — [Node type customization — Godot docs](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/node_type_customization.html)
- Houdini glTF ROP can write "Export Custom Attributes" (underscore-prefixed point attributes) and "Export Extras" (dictionary attributes as glTF properties) and can build hierarchy from a path attribute — [glTF ROP docs — SideFX](https://www.sidefx.com/docs/houdini/nodes/out/gltf.html); Godot 4.4+ imports glTF extras to node/mesh/material metadata — [godotengine/godot PR 86183, 2024](https://github.com/godotengine/godot/pull/86183)
- Labs VAT 3.0 Rigid-Body Dynamics mode bakes "packed pieces with RBD simulation data" to position/rotation textures; Godot_VAT3 implements `_VAT3MODE_RIGIDBODY_` — [Labs VAT 3.0 ROP docs — SideFX](https://www.sidefx.com/docs/houdini/nodes/out/labs--vertex_animation_textures-3.0.html); [G4ND44/Godot_VAT3](https://github.com/G4ND44/Godot_VAT3)
- Houdini has native Packed and Tetrahedron primitive types; packed primitives are "a lightweight reference to geometry stored somewhere else" — [Primitive types — SideFX docs, accessed 2026](https://www.sidefx.com/docs/houdini/model/primitives.html)

### Inferences
- A Houdini-authored support graph maps directly onto a Blast-style runtime: nodes = pieces (`name`), edges = constraint primitives (two points whose `name` values are the piece ids), edge weight = `strength` (−1 = unbreakable = "world anchor"/support), material presets from the Material Fracture type. Serialise it with a small hython script (iterate constraint prims, write JSON) or as glTF extras on the destructible's root node; either is readable by an `EditorScenePostImport` script on Godot 4.4+.
- Proxy hulls from Houdini's Convex Decomposition (per piece via "Use Piece Attribute") can be exported as child nodes named `<piece>-convcolonly`, avoiding Godot's V-HACD at import; alternatively let Godot run V-HACD via `-convcolonly`. Houdini gives you offline control (Max Concavity, PolyReduce) that Godot's importer does not expose per piece.
- Bullet bakes from the RBD Bullet Solver are for cinematic/background destruction (VAT rigid mode, or transform animation clips in glTF); the `broken` group can also be used offline to *tune* strengths before shipping the static graph.
- Houdini's glue `propagation_rate`/`half_life` describe Bullet-solver-specific impulse propagation; the runtime will need its own equivalent — only `strength` and topology transfer 1:1.

### Gaps
- No documented Houdini node exports an RBD constraint network as JSON or glTF; the export is a custom script (not verified against a specific example).
- The docs do not say whether Houdini's Convex Decomposition SOP uses V-HACD; treat "Houdini vs Godot V-HACD" quality comparison as unverified.
- Numeric mapping between Houdini glue `strength` (impulse units in Bullet) and Jolt/custom runtime units is undocumented.

## Key question 4: FEM and soft bodies (FEM solver, Vellum, tetrahedral meshing, exporting tet meshes, existing tet/FEM formats a runtime could load)

### Takeaway
Houdini can author tetrahedral meshes (Tet Embed, Tet Conform, Tetrahedralize) for its FEM Solid Object (elastic solids with "chipping, crumbling, and shattering") and for Vellum Tetrahedral Softbody (soft-distance edge springs plus tetrahedral volume constraints). Tets are a native Houdini primitive type; there is no game-oriented tet export format in Houdini, so a GDExtension FEM runtime would load a custom or TetGen-style (`.node`/`.ele`) file written from hython.

### Cited Findings
- Houdini's FEM solver produces "high-quality simulations of elastic materials", is "specifically well suited for the realistic simulation of highly nonlinear materials with strong local volume preservation, such as organic tissues", handles "solid objects, represented by tetrahedra (tets)", polygonal shells and polylines, and supports "bending, elasticity, internal mass, chipping, crumbling, and shattering"; the FEM Solid Object "expects a geometry that exists entirely of tets" — [About finite elements — SideFX docs, accessed 2026](https://www.sidefx.com/docs/houdini/finiteelements/about.html)
- "To create a simulation tet mesh, use Tet Embed or use Remesh in combination with Tet Conform. The Tet Embed SOP is usually the most effective option for finite element simulation"; FEM Validate SOP is "strongly recommended" for inspecting tet quality — [Creating simulation meshes for use with FEM — SideFX docs](https://www.sidefx.com/docs/houdini/finiteelements/geometry.html); Tet Conform is to be used instead of Tetrahedralize "to convert surface meshes into solid tetrahedralizations" — [Tet Conform SOP docs — SideFX](https://www.sidefx.com/docs/houdini/nodes/sop/tetconform.html)
- Tet Embed 2.0 generates "a simplified tetrahedral mesh that covers the input mesh"; parameters Base Size, Max Tet Scale, Min Triangle Scale, Local Scaling, Use Remesh, Voxel Size, Max Resolution, Add Surface Triangles, Enlarge to Cover Input Mesh; it transfers the `fracturepart` and `Cd` attributes; workflow pairs original mesh as Embedded Geometry with the tet mesh as Initial Geometry on the Solid Object — [Tet Embed 2.0 SOP docs — SideFX, accessed 2026](https://www.sidefx.com/docs/houdini/nodes/sop/tetembed.html)
- Vellum tetrahedral softbody: "Soft Distance constraints are created along each tetrahedral edge to act as springs … and Tetrahedral Volume constraints are created to maintain the volume of each tetrahedron"; the shelf tool "will polyreduce, remesh to create a low-res proxy, and tetrahedralize the input geometry before simulation" — [Vellum softbodies — SideFX docs](https://www.sidefx.com/docs/houdini/vellum/softbody.html); [Vellum Tetrahedral Softbody shelf tool — SideFX docs](https://www.sidefx.com/docs/houdini/shelf/vellumtetsoftbody.html)
- Houdini lists "Tetrahedron" among its native primitive types — [Primitive types — SideFX docs](https://www.sidefx.com/docs/houdini/model/primitives.html)
- TetGen file formats: `.node` "a list of nodes", `.ele` "a list of tetrahedra" (by node indices), `.face` "a list of triangular faces", `.edge` "a list of boundary edges", `.smesh` "a simple piecewise linear complex", `.mesh` Medit format — [TetGen file formats — Hang Si / WIAS Berlin](https://wias-berlin.de/software/tetgen/fformats.html)
- hython can load .hip files and run Python against the `hou` module headlessly — [Command-line scripting — SideFX docs](https://www.sidefx.com/docs/houdini/hom/commandline.html)

### Inferences
- Houdini is a strong offline *tet-mesh generator and validator* (Tet Embed + FEM Validate) for a custom FEM/XPBD destruction GDExtension; the runtime format is whatever the team defines. `.node`/`.ele` (TetGen) is a minimal, widely parsed choice; writing it from hython is a few lines over `hou.Geometry` tetrahedron primitives.
- Houdini FEM material parameters and fracture behaviour are solver-specific; only the mesh, per-tet material ids (e.g. `fracturepart`) and rest state transfer to a runtime.

### Gaps
- I did not find any Houdini node that writes TetGen/VTK/MSH tet files directly; the "export via hython" route is inferred, not documented.
- I did not verify a Godot FEM/soft-body GDExtension that loads tet meshes (out of scope here; other research notes may cover runtime engines).
- FEM material parameter names (shape/volume stiffness, damping, fracture threshold) were not confirmed from the about page; they live on the FEM Solid Object DOP page which I did not open.

## Key question 5: Characters and animation (KineFX rigging, MotionClips, export to glTF, ragdoll generation and mapping to Godot PhysicalBone3D, APEX)

### Takeaway
KineFX can procedurally rig, edit motion (MotionClips) and export skinned characters and clips to glTF/FBX for Godot. Its ragdoll workflow (Configure Joints → Ragdoll Collision Shapes → Ragdoll Solver 2.0) authors per-joint cone-twist limits (dictionary attribute; twist/up axes from rotation order) and per-joint convex-hull/capsule collision shapes as packed primitives with `name` — all readable data, but there is no exporter to Godot's PhysicalBone3D; a script must map limits to Godot's joint types (NONE/PIN/CONE/HINGE/SLIDER/6DOF). APEX rigs are exported by baking through Scene Invoke into the FBX/glTF character ROPs; I found no runtime that evaluates APEX outside Houdini.

### Cited Findings
- MotionClips are "a geometry format made from packed geometry primitives that each store a pose of a skeleton animation"; nodes: MotionClip SOP, MotionClip Evaluate, MotionClip Retime, MotionClip Blend, MotionClip Sequence, MotionClip Extract Locomotion, plus pose insert/delete/cycle/extract utilities — [MotionClips — SideFX docs, accessed 2026](https://www.sidefx.com/docs/houdini/character/kinefx/motionclips.html)
- Skinned export: ROP GLTF Character Output SOP (skin from `boneCapture`, joints, animation clips, morph targets; introduced H19.0; no Draco) and ROP FBX Character/Animation Output SOPs — [ROP GLTF Character Output SOP — SideFX docs](https://www.sidefx.com/docs/houdini/nodes/sop/kinefx--rop_gltfcharacteroutput.html); [Getting animation and character data out of KineFX — SideFX docs](https://www.sidefx.com/docs/houdini/character/kinefx/exportcharacters.html)
- KineFX ragdoll workflow uses Configure Joint Limits SOP, Ragdoll Collision Shapes SOP and Ragdoll Solver SOP; "The joint limits are stored in a dictionary attribute on each point. The name of the dictionary attribute is set in the Output Configuration parameter on the Configure Joint Limits SOP"; limits become cone twist constraints; the solver outputs an "animated skeleton" blendable with input animation via "Match Local Transforms"/"Match World Transforms"; the page does not name the underlying engine — [Ragdoll simulations — SideFX docs (KineFX), accessed 2026](https://www.sidefx.com/docs/houdini/character/kinefx/ragdoll.html)
- Configure Joints: writes a dictionary point attribute (name set by "Output Configuration Attribute"); UI exposes X/Y/Z Angle Range; "For Ragdoll, it specifies the twist (direction to the child) and up (direction to pole vector) joint axes needed for the Cone Twist Constraint. For example, a rotation order of Rx Ry Rz assigns the twist axis to X and the up axis to Y"; valid dictionary keys are documented under the `solvephysfbik` VEX function — [Configure Joints SOP docs — SideFX, accessed 2026](https://www.sidefx.com/docs/houdini/nodes/sop/kinefx--configurejoints.html)
- Ragdoll Collision Shapes "Creates collision shapes for a KineFX skeleton to be used in a ragdoll RBD simulation"; "Generate Convex Hulls from Skin Geometry" (Shrinkwrap or Convex Decomposition, from each joint's capture region; "Max Concavity") or "Generate Basic Shapes"; parameters Group, Rest Pose Attribute, Display Collision Shapes, Display Intersections; output 2 is collision-shape geometry "expected to be in a packed geometry format" with a valid `name` primitive attribute — [Ragdoll Collision Shapes SOP docs — SideFX](https://www.sidefx.com/docs/houdini/nodes/sop/kinefx--ragdollcollisionshapes.html)
- The older Ragdoll Constraints SOP (deprecated, "replaced by Ragdoll Solver 2.0") documents the constraint model: cone twist constraints from Configure Joints limits, fallback pin/position-only constraints, parameters Softness, Constraint Force Mixing, Bias Factor, Relaxation Factor, Position CFM/ERP, and external Hard/Soft (Stiffness, Damping Ratio)/Glue (Strength) constraints — [Ragdoll Constraints SOP docs — SideFX](https://www.sidefx.com/docs/houdini/nodes/sop/kinefx--ragdollconstraints.html); Ragdoll Solver 2.0 page: [kinefx--ragdollsolver.html](https://www.sidefx.com/docs/houdini/nodes/sop/kinefx--ragdollsolver.html)
- Godot PhysicalBone3D joint types: JOINT_TYPE_NONE (0), PIN (1), CONE (2), HINGE (3), SLIDER (4), 6DOF (5); body properties `mass` (1.0), `friction` (0–1), `bounce` (0–1), `gravity_scale`, `linear_damp`, `angular_damp` (+ `_mode`); requires `get_bone_id() >= 0` and an active parent PhysicalBoneSimulator3D — [PhysicalBone3D class — Godot docs (stable), accessed 2026](https://docs.godotengine.org/en/stable/classes/class_physicalbone3d.html)
- APEX export (SideFX forum): "the approach would always be to use the Scene Invoke SOP in order to fetch that animated skeleton", then FBX Character ROP with static geometry, capture pose and animated pose; Houdini 21 adds an "Animation Catalog" (Edward, Feb 2026); the thread contains no discussion of running APEX graphs outside Houdini — [Exporting APEX animations into fbx, gltf etc. — SideFX forum, 2023–2026](https://www.sidefx.com/forum/post/433834/)

### Inferences
- Godot 4.4+ metadata import makes it possible to carry the Configure Joints dictionary (per-joint angle ranges, twist/up axes) into the glTF as `extras` on joint nodes (the character ROP docs do not list an extras option — verify; otherwise export a JSON sidecar from hython) and to build PhysicalBone3D + collision shapes in an `EditorScenePostImport` script: cone-twist → `JOINT_TYPE_CONE` (swing/twist spans), single-axis ranges → `JOINT_TYPE_HINGE`, asymmetric three-axis ranges → `JOINT_TYPE_6DOF`.
- Ragdoll Collision Shapes' packed hulls per joint export as extra mesh nodes named `<joint>-convcolonly`, letting Godot create ConvexPolygonShape3D children automatically.
- Houdini's ragdoll solver parameters (CFM/ERP/softness) are Bullet-style and do not map to Jolt; only limits, shapes, masses and hierarchy transfer.

### Gaps
- The exact dictionary keys of the Configure Joints output attribute were not confirmed (the doc points to the `solvephysfbik` VEX page, which I did not open).
- Whether ROP GLTF Character Output honours "Export Extras"/custom attributes was not visible in the fetched summary.
- No source confirms the physics engine behind Ragdoll Solver 2.0 (Bullet is named for the RBD Bullet Solver, not on the ragdoll page).
- I found no APEX runtime for game engines and no statement from SideFX that one exists.

## Key question 6: Procedural world (heightfields to Terrain3D/HTerrain, building generators, scattering/instancing into Godot MultiMeshInstance3D, EXT_mesh_gpu_instancing)

### Takeaway
Houdini HeightField Output writes 16/32-bit float EXR (deep raster) or packed PNG/RGBA layers with tiling, which Terrain3D and HTerrain both import (both recommend EXR or R16/RAW, 16/32-bit, and warn against 8-bit PNG). Labs Building Generator, Lot Subdivision, OSM tools and Physics Painter cover cities and set dressing offline. Instancing is the weak link: Godot does not convert EXT_mesh_gpu_instancing to MultiMeshInstance3D (proposal open since 2024), so scatter data must be delivered as points/extras and instanced by a post-import script, or via houdini2godot's instancers/HEGo's Terrain3D bridge.

### Cited Findings
- HeightField Output SOP exports height/mask layers as images; "Packed Raster" stores up to four layers in RGBA (e.g. PNG) and "Deep Raster" writes separate planes (EXR, .pic); "Type" options "8b Fixed", "16b Fixed", "16b Floating Point", "32b Floating Point"; per-layer "Output Range" No/Auto/Manual Remap with From/To Range; "Divide into tiled maps" with UDIM/UV Tile/Frames/XY Tile naming — [HeightField Output SOP docs — SideFX, accessed 2026](https://www.sidefx.com/docs/houdini/nodes/sop/heightfield_output.html)
- Terrain3D imports BMP, DDS, EXR, HDR, JPG, PNG, TGA, SVG, WebP, R16 (16-bit unsigned) and RAW plus TRES/RES; "Only use 16 or 32-bit height data. If your data is only 8-bit, it will look terraced"; PNG is 8-bit only; recommendation "Use exr or r16/raw", EXR should be "RGB not greyscale, 16 or 32-bit float, no transparency"; R16 needs manual min/max/dimensions; importer at `addons/terrain_3d/tools/importer.tscn` with `import_position`, `height_offset`, `import_scale`; max "1024 regions (32x32)" and for large imports region size > image width / 32; export to EXR/PNG/JPG/WebP/R16/RES — [Importing & Exporting Data — Terrain3D docs (stable), accessed 2026](https://terrain3d.readthedocs.io/en/stable/docs/import_export.html)
- HTerrain (Zylann) imports PNG, OpenEXR (16-bit half-float greyscale), XYZ, Radiance HDR and RAW (unsigned 16-bit); "Only exr or r16/raw are recommended for heightmaps" because Godot imports PNG as 8-bit; R16 "is read/writable by World Machine, Unity, Krita" — [Zylann/godot_heightmap_plugin, hterrain_data.gd and issue #327](https://github.com/Zylann/godot_heightmap_plugin/issues/327); [repo](https://github.com/Zylann/godot_heightmap_plugin)
- HEGo's API "can convert heightfields to Godot images and vice versa, used in HEGoNode3D to bridge to the Terrain3D plugin" — [peterprickarz/hego README](https://github.com/peterprickarz/hego)
- Labs Building Generator "Generates detailed building geometry from blockout meshes using modular components"; Labs Lot Subdivision "Divides polygons into panels"; Labs OSM Import/Filter/Buildings — [SideFX Labs docs index](https://www.sidefx.com/docs/houdini/labs/); SideFX tutorials: "Procedural City 1: Building Generator", "City Building with OSM Data" — [SideFX tutorials](https://www.sidefx.com/tutorials/procedural-city-1-building-generator/), [OSM](https://www.sidefx.com/tutorials/city-building-with-osm-data/)
- Godot lacks EXT_mesh_gpu_instancing→MultiMesh import (proposal #8787 open since 3 Jan 2024; issue #109280 open, 4.5.beta4) — [godot-proposals #8787](https://github.com/godotengine/godot-proposals/issues/8787); [godot issue #109280](https://github.com/godotengine/godot/issues/109280)
- houdini2godot exports TSCN/ESCN with "customized Godot instancers" — [Mandrake0/houdini2godot](https://github.com/Mandrake0/houdini2godot)
- Godot post-import scripts (`EditorScenePostImport._post_import`) can rewrite the scene — [Import configuration — Godot docs](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/import_configuration.html)

### Inferences
- Terrain: export 32-bit float EXR from HeightField Output (deep raster, no remap) and splat masks as packed PNG/EXR; Terrain3D's importer takes both; keep Houdini heightfield resolution a multiple of Terrain3D region size.
- Scatter: export scatter points (P, orient, scale, prototype id) as a point-cloud mesh or a JSON sidecar, then a post-import script fills `MultiMesh` buffers; this is the same data Houdini already produces for Unreal instancing.
- Physics props: Physics Painter output (settled packed transforms) exports as `-rigid` or static nodes for Jolt.

### Gaps
- I did not verify Terrain3D's behaviour on a Godot 4.8-dev fork nor which Terrain3D version HEGo targets.
- No source was found for a Houdini→Godot scatter/MultiMesh workflow beyond houdini2godot's README claim of "instancers".

## Key question 7: When is Houdini worth it versus Blender (Cell Fracture, glTF exporter)?

### Takeaway
Blender's official glTF exporter (Apache-2.0, bundled since 2.80) covers the same skinned/animated glTF path into Godot and Blender's Cell Fracture is still available (as an Extensions-platform add-on with limited support) for simple Voronoi fracture. Houdini earns its cost when you need material-aware fracture with an authored constraint graph, convex proxies per piece, ragdoll limit/shape generation from skin weights, tetrahedral meshing for FEM, heightfield/terrain pipelines, PDG batch variants, and VAT baking; for plain modelling, skinning and single-object fracture Blender is enough.

### Cited Findings
- glTF-Blender-IO is the "Official Khronos Group Blender glTF 2.0 importer and exporter", Apache-2.0, and "Blender 2.80 and higher bundle this addon in the main Blender install package" — [KhronosGroup/glTF-Blender-IO README](https://github.com/KhronosGroup/glTF-Blender-IO)
- Godot's docs give Blender-specific glTF guidance (e.g. enable "Data > Armature > Export Deformation Bones Only" when models contain blend shapes; pre-3.2 Blender did not export emissive textures) — [Available 3D formats — Godot docs](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html)
- Cell Fracture is no longer bundled: "Blender 4.2 LTS and later include only a handful of core add-ons"; Cell Fracture "is now offered as it is, with limited support", installed from the Extensions platform (version 0.2.1, Blender 4.2 LTS+), used via Object > Quick Effects > Cell Fracture — [Cell Fracture — Blender Extensions](https://extensions.blender.org/add-ons/cell-fracture/); [version history](https://extensions.blender.org/add-ons/cell-fracture/versions/); breakage reports on 4.0 — [blender-addons #105001](https://projects.blender.org/blender/blender-addons/issues/105001)
- Blender's geometry-node instances export as EXT_mesh_gpu_instancing but Godot imports them as separate MeshInstance3D nodes — [godot issue #109280](https://github.com/godotengine/godot/issues/109280)
- Houdini-only capabilities cited above: RBD Material Fracture material types and constraint network ([rbdmaterialfracture](https://www.sidefx.com/docs/houdini/nodes/sop/rbdmaterialfracture.html)), RBD Constraint Properties attributes ([rbdconstraintproperties](https://www.sidefx.com/docs/houdini/nodes/sop/rbdconstraintproperties.html)), Ragdoll Collision Shapes from skin weights ([kinefx--ragdollcollisionshapes](https://www.sidefx.com/docs/houdini/nodes/sop/kinefx--ragdollcollisionshapes.html)), Tet Embed ([tetembed](https://www.sidefx.com/docs/houdini/nodes/sop/tetembed.html)), HeightField Output ([heightfield_output](https://www.sidefx.com/docs/houdini/nodes/sop/heightfield_output.html)), ROP Fetch/PDG ([ropfetch](https://www.sidefx.com/docs/houdini/nodes/top/ropfetch.html)), Labs VAT 3.0 ([labs--vertex_animation_textures-3.0](https://www.sidefx.com/docs/houdini/nodes/out/labs--vertex_animation_textures-3.0.html))

### Inferences
- Cell Fracture produces pieces only; the support graph, per-piece proxies and strength values you need for a Blast-style runtime would have to be scripted in Blender Python, whereas Houdini produces them as first-class attributes. That is the decisive Houdini advantage for this game's destruction.
- For character skinning and clip export both tools reach Godot equally through glTF; Houdini adds procedural ragdoll shape/limit generation and MotionClip editing.
- Neither tool solves Godot's missing instancing import; both need a Godot-side post-import step.

### Gaps
- I could not extract the Blender manual's exporter feature list (custom properties→extras option name, GPU-instances toggle, Draco) because the manual page fetch returned only navigation; the exporter's capabilities are therefore cited only via the Khronos README and the Godot issue that observed EXT_mesh_gpu_instancing in Blender output.
