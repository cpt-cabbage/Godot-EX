### Inferences
- A hybrid controller is feasible today: a RigidBody3D (or PhysicalBone3D pelvis) with `custom_integrator = true` gives full per-tick control over velocity via `PhysicsDirectBodyState3D`, while ShapeCast3D/`cast_motion_into` supply ground/wall probing without per-call allocations.
- Because CharacterVirtual is unexposed, "Euphoria-like" body-vs-world interaction (being shoved, tripping) is better served by a dynamic body than by CharacterBody3D, which under Jolt is a kinematic query loop and is not seen by other bodies as mass.

## Joints and motors: what Jolt implements, ignores, and whether a spring/damper orientation drive exists

### Takeaway
Generic6DOFJoint3D under Jolt supports limits, velocity motors, and stiffness/damping springs, and this build adds a **quaternion orientation target** (`set_angular_target_rotation`) plus **drive force/torque limits** (merged upstream June 2026, milestone 4.8), so a PD/spring-damper orientation drive per joint is available natively without hand-applied torques. Hinge and cone-twist joints get only velocity motors (cone-twist only via unexposed Jolt-only params); "softness/bias/relaxation/ERP/restitution" style parameters are ignored with warnings.

- Generic6DOFJoint3D: linear limit softness, linear restitution, linear damping (`:377-387`); angular limit softness, angular damping, angular restitution, angular force limit, angular ERP (`:425-445`) — `modules/jolt_physics/joints/jolt_generic_6dof_joint_3d.cpp`.
- HingeJoint3D: bias, limit bias, softness, relaxation — `modules/jolt_physics/joints/jolt_hinge_joint_3d.cpp:208-231`.
- PinJoint3D: bias, damping, impulse clamp — `modules/jolt_physics/joints/jolt_pin_joint_3d.cpp:103-113`.
- SliderJoint3D: all softness/restitution/damping variants and angular limits ("Try using Generic6DOFJoint3D instead") — `modules/jolt_physics/joints/jolt_slider_joint_3d.cpp:267-362`.

**Jolt motor and spring semantics (vendored 5.6.0 headers).**
- `EMotorState`: Velocity "will drive to target velocity limited only by max force/torque"; Position "force = stiffness * (target_position - current_position) - damping * current_velocity"; PositionAndVelocity "force = stiffness * (target_position - current_position) + damping * (target_velocity - current_velocity)" — `thirdparty/jolt_physics/Jolt/Physics/Constraints/MotorSettings.h:18-21`. Defaults: `mSpringSettings { FrequencyAndDamping, 2.0f, 1.0f }`, force/torque limits ±FLT_MAX; asymmetric `SetForceLimits/SetTorqueLimits` exist — `:75-79,53-63`.
- `SpringSettings`: modes `FrequencyAndDamping`, `StiffnessAndDamping`, `MassNormalizedStiffnessAndDamping` ("acceleration mode … mass independent") — `thirdparty/jolt_physics/Jolt/Physics/Constraints/SpringSettings.h:17-19`; "If > 0 the constraint will be soft … If <= 0 … hard limits"; units "N / m for a linear spring and N m / rad for an angular spring"; ballpark "stiffness = mass * gravity / delta_spring_length" — `:51-69`.
- Jolt docs: "Valid frequencies are in the range (0, 0.5 * simulation frequency]" — [Jolt Architecture page](https://jrouwe.github.io/JoltPhysics/index.html).
- `SixDOFConstraint`: "Translation motors work in constraint space of body 1. Rotation motors work in constraint space of body 2 (!)"; `SetTargetOrientationBS` = `mConstraintToBody1.Conjugated() * inOrientation * mConstraintToBody2` — `thirdparty/jolt_physics/Jolt/Physics/Constraints/SixDOFConstraint.h:169-193`.
- Godot exposes only `StiffnessAndDamping` (default) or `FrequencyAndDamping` (Jolt-only flag); `MassNormalizedStiffnessAndDamping` is not mapped — `jolt_generic_6dof_joint_3d.cpp:176-190`.

### Inferences
- **Answer to the key question:** yes, in this build a joint can be driven toward a target orientation with a spring/damper entirely inside the solver: enable `angular_spring_*/enabled` with stiffness/damping on a Generic6DOFJoint3D, call `set_angular_target_rotation(q)` each physics tick with the animation's desired child-relative-to-parent rotation, and cap output with `angular_drive_*/torque_limit`. This is the Jolt "Position" motor (PD in the solver), which is implicit and therefore more stable than script-applied torques. Manual torques remain necessary only for hinge/cone-twist joints (velocity motors only) or for GodotPhysics.
- Because `SetTargetOrientationBS` is body-space, the target is simply `q = (basis_A.inverse() * basis_B_desired)` in body A's frame, matching the reviewer comment in PR #118997; no Euler decomposition is needed.
- Hinge `max_impulse → torque` uses an estimated step, so changing `physics_ticks_per_second` at runtime silently changes hinge motor strength; prefer 6DOF for driven joints.

### Gaps
- Whether `angular_spring_*` stiffness in Godot's `Generic6DOFJoint3D` inspector (`default 0.0`) needs the `damping` to be non-zero to count as "active" under Jolt (`HasStiffnessOrDamping` — `SpringSettings.h:44`) was not tested at runtime.
- No official doc page yet describes `set_angular_target_rotation` beyond the class reference; the 4.7 and 4.8 release pages fetched contain no physics notes.

## Ragdoll and skeleton: PhysicalBone3D, PhysicalBoneSimulator3D, Skeleton3D, and the SkeletonModifier3D family

### Takeaway
PhysicalBone3D is strictly kinematic-or-simulated (RIGID when simulating, KINEMATIC/STATIC otherwise) and has no built-in "follow animation" target; an active ragdoll must be assembled from PhysicalBone3D's 6DOF joint (springs + `get_joint_rid()` + the new server quaternion target) or from `_integrate_forces`. The modifier stack in this build is large (LookAt, SpringBone, Retarget, IK family incl. TwoBone/Chain/FABRIK/CCD/Jacobian/Spline, BoneConstraint family, BoneTwistDisperser, BoneSpaceAdjuster, LimitAngularVelocity) and runs after AnimationMixer with per-modifier `influence` blending.

### Cited Findings
**PhysicalBone3D / PhysicalBoneSimulator3D.**
- Methods: `_integrate_forces(state)` ("By default, it is called before the standard force integration, but the custom_integrator property allows you to disable the standard force integration"), `apply_central_impulse`, `apply_impulse`, `get_bone_id`, `get_joint_rid`, `get_simulate_physics`, `is_simulating_physics`; members incl. `body_offset, joint_offset, joint_rotation, joint_type (NONE/PIN/CONE/HINGE/SLIDER/6DOF), mass, friction, bounce, gravity_scale, linear/angular_damp(_mode), can_sleep, custom_integrator` — `doc/classes/PhysicalBone3D.xml:14-141`.
- Start: `reset_to_rest_position(); set_body_mode(BODY_MODE_RIGID); … body_set_state_sync_callback(_body_state_changed); set_as_top_level(true)` — `scene/3d/physics/physical_bone_3d.cpp` (`_start_physics_simulation`). Stop: `BODY_MODE_KINEMATIC` if the simulator is active, else `BODY_MODE_STATIC` with layer/mask 0 — same file (`_stop_physics_simulation`).
- Pose write-back: `_body_state_changed` calls the scripted `_integrate_forces` if overridden, then `simulator->set_bone_global_pose(bone_id, skeleton->get_global_transform().affine_inverse() * (global_transform * body_offset_inverse))` — `physical_bone_3d.cpp:805-836`.
- Rest pose read: `reset_to_rest_position` uses `simulator->get_bone_global_pose(bone_id)` — `physical_bone_3d.cpp:100-107`; the simulator caches skeleton poses on `pose_updated` — `scene/3d/physics/physical_bone_simulator_3d.cpp:43-52,90-92`.

### Inferences
- "Mixing simulated bones with animation" is officially supported only as (a) partial simulation of a bone subset via `physical_bones_start_simulation(names)` and (b) linear blending of the simulator's output with the animated pose via `influence`. - The PhysicalBone3D node already creates a 6DOF joint with angular springs when `joint_type = 6DOF`; the missing piece (quaternion target + torque limit) can be supplied by script using `get_joint_rid()` and `PhysicsServer3D.generic_6dof_joint_set_angular_target_rotation` / `generic_6dof_joint_set_param(rid, axis, G6DOF_JOINT_ANGULAR_DRIVE_TORQUE_LIMIT, v)` since those server enums are bound (`servers/physics_3d/physics_server_3d.cpp:404-405,435-436`). This is unverified at runtime but every link in the chain exists in the source.
- `LimitAngularVelocityModifier3D` and `SpringBoneSimulator3D` are the ready-made procedural-secondary-motion tools for a first-person rig (arms, head bob damping) and run at IDLE or PHYSICS rate as configured.

## Physics settings: tick rate, interpolation, Jolt project settings, CCD, sleeping, solver iterations, sub-stepping

### Takeaway
Defaults are 60 ticks/s with 8 max steps per frame, physics interpolation off (3D interpolation shipped in 4.4), Jolt solver at 10 velocity / 2 position iterations, CCD per body via `continuous_cd` (Jolt LinearCast), island sleeping on; Jolt runs exactly one collision step per Godot tick and exposes no sub-stepping setting, so raising fidelity means raising `physics_ticks_per_second`.

### Cited Findings
- `physics/common/physics_ticks_per_second` default 60; "CPU usage scales approximately with the physics tick rate … High tick rates give more accurate physics simulation, particularly for fast moving objects"; "it is recommended to also increase physics/common/max_physics_steps_per_frame if increasing physics_ticks_per_second significantly"; "Consider enabling physics interpolation if you change … to a value that is not a multiple of 60" — `doc/classes/ProjectSettings.xml:2734-2741`. `max_physics_steps_per_frame` default 8 (spiral-of-death explanation) — `:2717-2721`. Runtime equivalents `Engine.physics_ticks_per_second` — `doc/classes/Engine.xml:332-335`.
- `physics/common/physics_interpolation` default false; jitter fix "automatically disabled" when interpolation is on — `:2722-2733`. `physics/3d/physics_interpolation/scene_traversal` (DEFAULT/Legacy/Debug) — `:2671-2676`. `SceneTree.physics_interpolation`, `Node.physics_interpolation_mode`, `Node.reset_physics_interpolation` — `doc/classes/SceneTree.xml:290-293`, `doc/classes/Node.xml:873,1061-1065`. Node3D has `_get_global_transform_interpolated` — `scene/3d/node_3d.h:200-201`.
- 3D physics interpolation was a 4.4 feature: "By decoupling physics ticks and display frame rates, physics interpolation creates additional frames between the last physics position and the current one" — [Godot 4.4 release](https://godotengine.org/releases/4.4/); 4.5 moved it "from RenderingServer to SceneTree" — [Godot 4.5 release](https://godotengine.org/releases/4.5/). ### Inferences
- With no sub-stepping knob, stiff joint drives that need a smaller solver dt must come from a higher `physics_ticks_per_second` (and a matching `max_physics_steps_per_frame`), while physics interpolation keeps rendering smooth at any tick multiple.
- Jolt's spring-frequency ceiling (≤ 0.5 × tick rate) means a 60 Hz tick caps drive frequencies at 30 Hz; 120 Hz doubles that headroom.

### Gaps
- No measured CPU cost for Jolt at 120 or 240 Hz in Godot was found (no benchmark sources reachable); only the doc statement that CPU scales roughly linearly with tick rate.

## Godot's built-in Jolt module versus the godot-jolt GDExtension, and Jolt library features Godot does not expose

### Takeaway
The built-in module (since 4.4) is the maintained path; the GDExtension is in maintenance mode (supports 4.3–4.6) and still has features the module lacks (its own joint nodes with soft limits, breakability, per-joint solver iterations). Jolt's higher-level ragdoll API (`Ragdoll::DriveToPoseUsingMotors/Kinematics`), `CharacterVirtual`, several constraint types, and `MassNormalized` springs are compiled in but unexposed.

### Cited Findings
- "As of Godot 4.4, this integration of Jolt Physics is built into Godot itself, in the form of an engine module"; the extension "supports Godot versions between 4.3 and 4.6"; the built-in module lacks "the joint interface changes (JoltHingeJoint3D, etc.) that this extension exposes" (breakable joints, soft limits, per-joint solver iteration control); MIT licence — [godot-jolt README](https://raw.githubusercontent.com/godot-jolt/godot-jolt/master/README.md).
- Godot docs: settings moved from `physics/jolt_3d` to `physics/jolt_physics_3d` with renames (`sleep/enabled → simulation/allow_sleep`, `collisions/use_shape_margins → collisions/collision_margin_fraction`); the extension "is now considered in maintenance mode"; module supports `run_on_separate_thread` ("experimental") — [Using Jolt Physics](https://docs.godotengine.org/en/latest/tutorials/physics/using_jolt_physics.html).
- Proposal history: "Recognize Godot Jolt … as an officially endorsed add-on" (closed, 311 👍) — [godot-proposals #7308](https://github.com/godotengine/godot-proposals/issues/7308); "Implement extra physics constraints (joints) from Jolt" (open since 2024-12-12; asks for DistanceConstraint, FixedConstraint, PulleyConstraint, GearConstraint "etc etc"; "Constraints are hard to implement in a stable manner") — [godot-proposals #11338](https://github.com/godotengine/godot-proposals/issues/11338); "Expose advanced Jolt soft-body constraint configuration" (open, 2026-09-15) — [godot-proposals #15526](https://github.com/godotengine/godot-proposals/issues/15526).
- Unexposed Jolt ragdoll API: `Ragdoll::DriveToPoseUsingKinematics(pose, dt)` and `DriveToPoseUsingMotors(pose)` / `DriveToPoseUsingMotors(prevPose, pose, dt)` ("Drives both to target position and velocity") — `thirdparty/jolt_physics/Jolt/Physics/Ragdoll/Ragdoll.h:180-193`. Implementation sets `SetSwingMotorState(EMotorState::Position)`, `SetTwistMotorState(EMotorState::Position)`, `SetTargetOrientationBS(joint_state.mRotation)` for SwingTwist constraints and `SetMotorState(Position)` + `SetTargetOrientationBS` for Hinge — `thirdparty/jolt_physics/Jolt/Physics/Ragdoll/Ragdoll.cpp` (function `Ragdoll::DriveToPoseUsingMotors`). `grep -rn Ragdoll modules/jolt_physics` finds nothing (not wrapped).
- Jolt's sample drives a ragdoll to an animation each step: `mAnimation->Sample(mTime, mPose);` then `mRagdoll->DriveToPoseUsingMotors(mPose)` or `DriveToPoseUsingMotors(mPrevPose, mPose, inParams.mDeltaTime)`, and measures pose error — [PoweredRigTest.cpp, JoltPhysics samples](https://raw.githubusercontent.com/jrouwe/JoltPhysics/master/Samples/Tests/Rig/PoweredRigTest.cpp).
- SwingTwist constraint has swing/twist `MotorSettings`, `SetTargetOrientationBS`, and `mMaxFrictionTorque` ("torque to apply as friction when the constraint is not powered by a motor") — `thirdparty/jolt_physics/Jolt/Physics/Constraints/SwingTwistConstraint.h:56-60,114-145`; Godot's cone-twist wrapper never enters `Position` mode — `jolt_cone_twist_joint_3d.cpp:91-101`.
- Jolt HelloWorld guidance: "60 Hz is a good rate to update the physics system"; "If you take larger steps than 1 / 60th of a second you need to do multiple collision steps in order to keep the simulation stable. Do 1 collision step per 1 / 60th of a second (round up)" — [HelloWorld.cpp, JoltPhysics](https://raw.githubusercontent.com/jrouwe/JoltPhysics/master/HelloWorld/HelloWorld.cpp).

### Inferences
- For a powered ragdoll, Godot's Generic6DOF path reproduces Jolt's own `DriveToPoseUsingMotors` semantics (Position motor + body-space quaternion target) one joint at a time; the missing convenience is a `SkeletonPose`-level driver and the SwingTwist motor, which a small module patch could add since the fork already builds Jolt in-tree.
- The `(prevPose, pose, dt)` variant (PositionAndVelocity) is not reachable from Godot because there is no API to set a target angular velocity together with a quaternion target on the 6DOF joint's spring path — the Godot motor "target velocity" enables the *Velocity* term (state `PositionAndVelocity` only when both flags on — `jolt_generic_6dof_joint_3d.cpp:112-121`), so feeding the animation's angular velocity into `angular_motor_*/target_velocity` alongside the spring would emulate it; untested.

### Gaps
- Jolt's Samples README (list of Rig/Character tests) returned HTTP 404 at `Samples/README.md`; sample coverage was verified only via `PoweredRigTest.cpp`.
- Jolt's per-frequency recommendations for ragdoll motors (documented only in sample code/GitHub discussions) could not be searched.

## Recommended tick rate for stable PD joint drives and the cost of 120/240 Hz

### Takeaway
Documented guidance converges on 60 Hz as the baseline (Godot default, Jolt's recommendation), with community active-ragdoll builds degrading below ~45–60 ticks; Jolt caps usable spring frequency at half the tick rate, and Godot's docs state CPU cost scales roughly linearly with tick rate, so 120 Hz is a defensible choice for stiff drives if `max_physics_steps_per_frame` is raised and physics interpolation is enabled. No measured 120/240 Hz Jolt benchmark for Godot was found.

### Cited Findings
- Godot default 60 ticks/s; "CPU usage scales approximately with the physics tick rate … at very low tick rates (usually below 30), physics behavior can break down"; raise `max_physics_steps_per_frame` (default 8) when raising ticks — `doc/classes/ProjectSettings.xml:2717-2741`, `doc/classes/Engine.xml:332-335`.
- Jolt: "60 Hz is a good rate to update the physics system"; "Do 1 collision step per 1 / 60th of a second (round up)" — [HelloWorld.cpp](https://raw.githubusercontent.com/jrouwe/JoltPhysics/master/HelloWorld/HelloWorld.cpp); "Valid frequencies are in the range (0, 0.5 * simulation frequency]" for frequency-mode springs — [Jolt Architecture page](https://jrouwe.github.io/JoltPhysics/index.html); frequency ≤ 0 makes the constraint "as hard as the time step / the number of velocity / position solver steps allows" — `thirdparty/jolt_physics/Jolt/Physics/Constraints/SpringSettings.h:51-53`.
- Godot's Jolt space always runs one collision step per tick — `modules/jolt_physics/spaces/jolt_space_3d.cpp:196`; solver iterations default 10/2 — `jolt_project_settings.cpp:37-38`.
- Community: active ragdoll "randomly flop around" at 30 ticks; acceptable "above 45 ticks" after moving to server calls with fixed 1/60 delta and physics-mode skeleton callback (Godot 4.7) — [forum topic 143292](https://forum.godotengine.org/t/143292).
- Hinge motor impulse→torque conversion assumes a constant timestep — `modules/jolt_physics/joints/jolt_hinge_joint_3d.cpp:195-197,235-238`.
- Physics interpolation decouples render rate from tick rate; recommended when tick rate is not a multiple of 60 — `ProjectSettings.xml:2740`; tick tiers "High tick rates (60+)" for fast-moving physics — [Using physics interpolation](https://docs.godotengine.org/en/latest/tutorials/physics/interpolation/using_physics_interpolation.html).

### Inferences
- For a ~15-body ragdoll with 6DOF Position motors, 120 Hz roughly doubles solver work per second (linear scaling per Godot docs) but halves the effective dt for the implicit spring, raising the stable stiffness/frequency ceiling to 60 Hz-equivalent drives; 240 Hz quadruples cost and mainly benefits very stiff, high-speed contact (superhuman sprint into walls) — worth profiling rather than assuming.
- Prefer solver-side springs (implicit) over `_integrate_forces` PD torques (explicit) at any tick rate; if explicit torques are used, clamp with `PARAM_ANGULAR_DRIVE_TORQUE_LIMIT`-style caps in script and keep `physics_ticks_per_second` fixed at runtime because hinge limits and Baumgarte tuning are step-dependent.

### Gaps
- No primary source quantifies Jolt's CPU cost at 120 vs 240 Hz inside Godot; the user should profile with the Godot profiler's "Physics Process" time and Jolt's `max_body_pairs`/`max_contact_constraints` counters.
- Jolt's own ragdoll motor tuning values (frequency/damping used in `PoweredRigTest` rig assets) live in sample data files (`Assets/Human/*.tof`) not fetched.
