## Key question 1: Movement math (Quake III, GoldSrc/Source, Titanfall/Apex, Mirror's Edge, Dying Light, Ghostrunner, Neon White, Boneworks)

### Takeaway
The whole "momentum FPS" lineage (Quake III, Half-Life, Source, and by descent Titanfall/Apex and the surf/jump-map culture Neon White cites) runs on one 6-line acceleration rule: project velocity onto the wish direction, add `accel * wishspeed * dt` but never more than the shortfall, with a separate friction pass that decays speed exponentially above `stopspeed` and linearly below it. Air control is the same rule with a small `accel` (Quake III) or a hard 30-unit cap on the projected wish speed (GoldSrc/Source), which is exactly what makes air-strafing gain speed. Jump is an instant vertical velocity `sqrt(2 g h)`; Source adds a clipped forward boost on jump.

### Cited Findings

#### Quake III Arena (id Software, 1999; GPL source 2005)
- Default movement constants in `bg_pmove.c`: `pm_stopspeed = 100.0f; pm_duckScale = 0.25f; pm_swimScale = 0.50f; pm_wadeScale = 0.70f; pm_accelerate = 10.0f; pm_airaccelerate = 1.0f; pm_wateraccelerate = 4.0f; pm_flyaccelerate = 8.0f; pm_friction = 6.0f; pm_waterfriction = 1.0f; pm_flightfriction = 3.0f; pm_spectatorfriction = 5.0f;` — [Quake III Arena source, code/game/bg_pmove.c, id Software](https://raw.githubusercontent.com/id-Software/Quake-III-Arena/master/code/game/bg_pmove.c)
- Header constants in `bg_local.h`: `MIN_WALK_NORMAL 0.7f` (cos of max walkable slope, about 45.6 degrees), `STEPSIZE 18`, `JUMP_VELOCITY 270`, `TIMER_LAND 130` (ms), `OVERCLIP 1.001f` — [Quake III Arena source, code/game/bg_local.h](https://raw.githubusercontent.com/id-Software/Quake-III-Arena/master/code/game/bg_local.h)
- Server defaults: `g_speed "320"`, `g_gravity "800"` (units/s and units/s^2) — [Quake III Arena source, code/game/g_main.c](https://raw.githubusercontent.com/id-Software/Quake-III-Arena/master/code/game/g_main.c)
- `PM_Accelerate` (verbatim core):
  ```c
  currentspeed = DotProduct (pm->ps->velocity, wishdir);
  addspeed = wishspeed - currentspeed;
  if (addspeed <= 0) return;
  accelspeed = accel*pml.frametime*wishspeed;
  if (accelspeed > addspeed) accelspeed = addspeed;
  for (i=0 ; i<3 ; i++) pm->ps->velocity[i] += accelspeed*wishdir[i];
  ```
  — [bg_pmove.c](https://raw.githubusercontent.com/id-Software/Quake-III-Arena/master/code/game/bg_pmove.c)
- `PM_Friction` (verbatim core): on ground and not on a `SURF_SLICK` surface and not in knockback, `control = speed < pm_stopspeed ? pm_stopspeed : speed; drop += control*pm_friction*pml.frametime;` then `newspeed = speed - drop; if (newspeed < 0) newspeed = 0; newspeed /= speed;` and velocity is scaled by `newspeed`. Speeds below 1 are zeroed. Water adds `speed*pm_waterfriction*waterlevel*frametime`. When walking, the vertical component is ignored ("ignore slope movement") — [bg_pmove.c](https://raw.githubusercontent.com/id-Software/Quake-III-Arena/master/code/game/bg_pmove.c)
- `PM_CmdScale`: input is scaled so that diagonal input does not exceed max speed: `scale = pm->ps->speed * max / (127.0 * total)` where `max` is the largest axis magnitude and `total` the vector length of the three command axes — [bg_pmove.c](https://raw.githubusercontent.com/id-Software/Quake-III-Arena/master/code/game/bg_pmove.c)
- `PM_WalkMove`: after `PM_CheckJump`, calls `PM_Friction`, builds `wishvel` from forward/right clipped to the ground plane (`PM_ClipVelocity(..., OVERCLIP)`), clamps ducked speed to `speed * pm_duckScale`, uses `pm_airaccelerate` instead of `pm_accelerate` when on `SURF_SLICK` or during `PMF_TIME_KNOCKBACK`, then clips the resulting velocity to the ground plane while preserving its magnitude (`VectorNormalize` then `VectorScale` by the pre-clip length), then `PM_StepSlideMove(qfalse)` — [bg_pmove.c](https://raw.githubusercontent.com/id-Software/Quake-III-Arena/master/code/game/bg_pmove.c)
- `PM_AirMove`: calls `PM_Friction()` (which does nothing in the air unless in water/flight), builds a horizontal `wishvel`, `PM_Accelerate(wishdir, wishspeed, pm_airaccelerate)`, clips to the ground plane if `pml.groundPlane`, then `PM_StepSlideMove(qtrue)` (gravity applied inside) — [bg_pmove.c](https://raw.githubusercontent.com/id-Software/Quake-III-Arena/master/code/game/bg_pmove.c)
- `PM_CheckJump`: requires `cmd.upmove >= 10`, refuses if `PMF_JUMP_HELD` (no auto-repeat), sets `velocity[2] = JUMP_VELOCITY` (an assignment, not an addition), clears ground, sets `PMF_BACKWARDS_JUMP` if moving backwards — [bg_pmove.c](https://raw.githubusercontent.com/id-Software/Quake-III-Arena/master/code/game/bg_pmove.c)
- `PM_ClipVelocity` (verbatim): `backoff = DotProduct(in, normal); if (backoff < 0) backoff *= overbounce; else backoff /= overbounce; out = in - normal*backoff;` — [bg_pmove.c](https://raw.githubusercontent.com/id-Software/Quake-III-Arena/master/code/game/bg_pmove.c)
- `PM_SlideMove`/`PM_StepSlideMove` (`bg_slidemove.c`): up to `numbumps = 4` collision iterations and `MAX_CLIP_PLANES = 5`; when gravity is on, the integrated velocity is averaged (`velocity[2] = (velocity[2] + endVelocity[2]) * 0.5`) for the move; velocity is clipped against each touched plane, slides along the crease of two planes using the cross product of their normals, and stops dead if a third plane is entered; if `pm_time` is set the original velocity is restored after the move. Stepping: if the plain slide is blocked, and the player is not moving upward on a ground plane and the ground below is walkable (normal dot up >= 0.7), trace up `STEPSIZE`, re-slide, trace down; step events fire for height deltas > 2 (EV_STEP_4/8/12/16 at <7, <11, <15, else) — [Quake III Arena source, code/game/bg_slidemove.c](https://raw.githubusercontent.com/id-Software/Quake-III-Arena/master/code/game/bg_slidemove.c)

#### GoldSrc / Half-Life 1 (Valve, 1998; source released 2013)
- `PM_Accelerate` is the Quake rule multiplied by surface friction: `accelspeed = accel * pmove->frametime * wishspeed * pmove->friction;` — [Half-Life SDK, pm_shared/pm_shared.c, Valve](https://raw.githubusercontent.com/ValveSoftware/halflife/master/pm_shared/pm_shared.c)
- `PM_AirAccelerate` caps the projected wish speed: `if (wishspd > 30) wishspd = 30; currentspeed = DotProduct(velocity, wishdir); addspeed = wishspd - currentspeed; if (addspeed <= 0) return; accelspeed = accel * wishspeed * frametime * friction; if (accelspeed > addspeed) accelspeed = addspeed;` (note `accelspeed` uses the uncapped `wishspeed`, `addspeed` uses the capped `wishspd`) — [pm_shared.c](https://raw.githubusercontent.com/ValveSoftware/halflife/master/pm_shared/pm_shared.c)
- `PM_Friction` has "edge friction": a trace 16 units ahead of the player and 34 units down; if it finds nothing (`trace.fraction == 1.0`) friction is multiplied by `movevars->edgefriction`, so you stop faster at ledges — [pm_shared.c](https://raw.githubusercontent.com/ValveSoftware/halflife/master/pm_shared/pm_shared.c)
- `PM_WalkMove` zeroes vertical velocity around ground acceleration (`velocity[2] = 0; PM_Accelerate(...); velocity[2] = 0;`) and clamps `wishspeed` to `maxspeed` — [pm_shared.c](https://raw.githubusercontent.com/ValveSoftware/halflife/master/pm_shared/pm_shared.c)
- `PM_Jump`: `velocity[2] = sqrt(2 * 800 * 45.0)` (a 45-unit jump at gravity 800, i.e. 268.3 u/s); long-jump module: horizontal `forward * PLAYER_LONGJUMP_SPEED(350) * 1.6` and `velocity[2] = sqrt(2 * 800 * 56.0)`, with a `-5` degree view punch — [pm_shared.c](https://raw.githubusercontent.com/ValveSoftware/halflife/master/pm_shared/pm_shared.c)
- Bunny-hop limiter `PM_PreventMegaBunnyJumping`: `BUNNYJUMP_MAX_SPEED_FACTOR 1.7f`; if speed exceeds `1.7 * maxspeed`, velocity is scaled by `(maxscaledspeed / spd) * 0.65` — [pm_shared.c](https://raw.githubusercontent.com/ValveSoftware/halflife/master/pm_shared/pm_shared.c)
- Other constants: `STOP_EPSILON 0.1`, `MAX_CLIP_PLANES 4`, `PLAYER_DUCKING_MULTIPLIER 0.333`, `MAX_CLIMB_SPEED 200` — [pm_shared.c](https://raw.githubusercontent.com/ValveSoftware/halflife/master/pm_shared/pm_shared.c)

#### Source engine (Source SDK 2013, Valve)
- Default movevars: `sv_gravity` "600" for HL2 builds, "800" otherwise; `sv_stopspeed` "100"; `sv_maxspeed` "320"; `sv_accelerate` "10" (a compile-time branch uses "7"); `sv_airaccelerate` "10"; `sv_wateraccelerate` "10"; `sv_waterfriction` "1"; `sv_friction` "4"; `sv_bounce` "0"; `sv_maxvelocity` "3500"; `sv_stepsize` "18"; `sv_backspeed` "0.6" ("How much to slow down backwards motion") — [Source SDK 2013, src/game/shared/movevars_shared.cpp](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/game/shared/movevars_shared.cpp)
- `CGameMovement::AirAccelerate` caps at `GetAirSpeedCap()`; `virtual float GetAirSpeedCap( void ) { return 30.f; }` — [gamemovement.cpp](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/game/shared/gamemovement.cpp) and [gamemovement.h](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/game/shared/gamemovement.h)
- Jump: `GAMEMOVEMENT_JUMP_HEIGHT 21.0f // units`, `GAMEMOVEMENT_JUMP_TIME 510.0f // ms approx - based on the 21 unit height jump`, `GAMEMOVEMENT_DUCK_TIME 1000.0f // ms` — [gamemovement.h](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/game/shared/gamemovement.h)
- `CheckJumpButton`: `flMul = sqrt(2 * GetCurrentGravity() * GAMEMOVEMENT_JUMP_HEIGHT)` (optimized builds hard-code `160.0f // approx. 21 units` for HL2's gravity 600, `268.3281572999747f` for gravity 800); when ducking `velocity.z = flGroundFactor * flMul`, otherwise `velocity.z += flGroundFactor * flMul` (added, so upward platform velocity carries); `flGroundFactor` is the surface's `jumpFactor`. In HL2 single player a forward bonus is added: `flSpeedBoostPerc = (!sprinting && !ducked) ? 0.5f : 0.1f; flSpeedAddition = fabs(forwardmove * flSpeedBoostPerc); flMaxSpeed = maxspeed * (1 + flSpeedBoostPerc);` and the addition is clipped so the 2D speed does not exceed `flMaxSpeed` ("That bonus is clipped to not accumulate over time") — [gamemovement.cpp](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/game/shared/gamemovement.cpp)
- Ground friction uses `sv_friction * player->m_surfaceFriction` and the `sv_stopspeed` control speed (one branch doubles it: `sv_stopspeed * 2.0f`) — [gamemovement.cpp](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/game/shared/gamemovement.cpp)

### Inferences
- Time to top speed: with `pm_accelerate = 10`, Quake III reaches `wishspeed` from rest in `1/pm_accelerate = 0.1 s` on the ground (friction aside), because `accelspeed = 10 * dt * wishspeed`. Source with `sv_accelerate 10` is identical. Ground friction above `stopspeed` is an exponential decay with time constant `1/pm_friction` (0.167 s in Q3 at 6; 0.25 s in Source at 4); below `stopspeed` it becomes a linear decay of `stopspeed * friction` units/s^2 (600 u/s^2 in Q3), which is why Quake characters snap to a halt instead of creeping.
- Why the 30-unit cap makes air-strafing gain speed: in GoldSrc/Source the per-tick gain along `wishdir` is at most `30 - dot(v, wishdir)`. Strafing perpendicular to velocity makes the dot ~0, so ~30 u/s is added sideways each tick, and `|v|` grows by about `sqrt(|v|^2 + 30^2) - |v| ≈ 450/|v|` per tick (about +93 u/s per second at 320 u/s and 66 ticks/s). In Quake III there is no cap but `pm_airaccelerate = 1`, so the same geometry applies with `accelspeed = wishspeed * dt`.
- Jump heights implied by the constants: Q3 `270^2 / (2*800) = 45.6` units; HL1 exactly 45 units by construction; HL2 21 units (about 1.75 ft at the 12 units/ft the HL2 comments use). The HL2 jump is deliberately low relative to the 72-unit player; the forward boost on jump (up to +50% of max speed, clipped) is what makes HL2 jumps feel like they carry momentum.
- Unit conversions for reuse: the Apex wiki's 199.53 units = 5.07 m/s gives 39.35 units per metre, i.e. one Source/Respawn unit is one inch (2.54 cm), consistent with the HL2 `shareddefs.h` comments using 12 units per foot. So Source `sv_maxspeed 320` is 8.1 m/s, `sv_gravity 600` is 15.2 m/s^2 (Quake's 800 is 20.3 m/s^2, both well above 9.81), and jump velocity 160 u/s is 4.1 m/s.
- Design pattern shared by Titanfall, Ghostrunner and Mirror's Edge: momentum is preserved by chaining state transitions (slide to jump to slide, wall-run to jump) and each transition adds a small fixed boost, while the ground state applies friction. The boost on entering a slide is the same "snap into a new state, keep velocity, reduce control" idea Haggerty describes; the "cannot stop or change direction as easily" is a lower ground acceleration during the slide.
- Mirror's Edge's 8-second acceleration to top speed (CritPoints) is an outlier versus Quake's 0.1 s; combined with its instant stop, it is asymmetric: slow to build, fast to lose, easy to stop. That asymmetry is exactly what a "momentum as reward" game wants and what a "physics-realistic" game must decide whether to keep.

## Key question 2: Grab and climb mechanics and their inputs

### Takeaway
Two families exist. Parkour FPSs (Mirror's Edge, Dying Light) use one context-sensitive "up/parkour" button and auto-grab based on real-time geometry scans (Dying Light: 200+ raytraces per frame after abandoning 50,000 hand-placed hooks). Physics-body games (Grow Home, Human: Fall Flat, Jusant, Boneworks) map one grip control per hand (left/right trigger or mouse button), hold-to-grip, release-to-let-go, and let the body physics do the climbing, which the developers describe as giving "a very physical connection to the grabbing".

### Cited Findings
- Dying Light: the first approach was hand-placed "hooks" ("invisible interactive points where the player could grab and pull themselves up"); "Pretty soon we had something like 50,000 hooks on one segment of the map and any movement or change in the level design would bring this all tumbling down." The replacement "analyses the environment in front of you in real-time and, based on certain geometric conditions, decides if you can climb the object." (Kulon) — [MCV/Develop](https://mcvuk.com/development-news/the-vaulting-dead-implementing-first-person-parkour-in-dying-light/); "more than 50,000 of these interactive hooks on a map that at the time was about one-fourth the size of what we wanted" — [Game Developer deep dive](https://www.gamedeveloper.com/design/game-design-deep-dive-i-dying-light-i-s-natural-movement-system); detection costs "over 200 [raytraces] per frame" — [GDC Q&A](https://gdconf.com/news/speaker-qa-bartosz-kulon-explains-turning-nba-dreams-game-dev-expertise). ### Inferences
- The two input philosophies map onto the user's two goals. A single context "up" button (Mirror's Edge, Dying Light, Apex mantle) maximises flow but hides the decision from the player; a dedicated per-hand grip (Grow Home, Jusant, Human: Fall Flat, Boneworks) makes grabbing an explicit, timed commitment, which is what a "high jump unlocks before fall tolerance, so you must grab to survive" gate needs. Jusant and Grow Home show that one grip per trigger is learnable in a non-VR game; Jusant explicitly rejected adding leg controls as "too complicated", and Human: Fall Flat pairs the grip with camera-look to steer the arms, which is the natural analogue of a mouse-look FPS with a grab on right mouse.
- Detection: Dying Light's evolution (hand-placed hooks to a real-time geometric scan of 200+ traces evaluating "height, speed and position") and Mirror's Edge's vaulting (fixed metrics to fully dynamic selection "based on height, speed and obstacle shape") both converged on runtime scans keyed to the player's speed, not on markup. For a Godot/Jolt build, this is a set of shape casts/ray casts ahead and above the capsule each physics tick; the 200/frame figure indicates the budget Techland accepted before optimising with grouped parallel traces.
- Celeste's stamina numbers (110 units; climbing up burns 100 in 2.2 s; hanging still burns 10/s; a climb-jump costs 27.5, so four per refill) are a well-liked, reproducible baseline for a stamina-gated grab; Jusant's playtests rejected per-arm gauges and non-regenerating chunks as punitive or hard to read, which argues for one shared meter with visible resting recovery.

## Key question 3: Kinematic versus dynamic character controllers

### Takeaway
Every physics vendor consulted (NVIDIA PhysX, Jolt, Godot) recommends a kinematic "collide and slide" controller for players and documents why a rigid-body controller misbehaves: tunneling at speed, indirect control through forces, contradictory friction needs, residual bounce at zero restitution, ground-sticking, and poor upright constraints. Jolt ships both (`Character` = rigid body with translation-only DOFs, 80 kg; `CharacterVirtual` = query-based, 70 kg, with `WalkStairs`/`StickToFloor` and an optional inner rigid body so the world still sees a body), and Boneworks shows a fully simulated body is possible if you accept "pure simulation" (jumps from foot thrust, 82 kg mass) as the design.

### Cited Findings
- PhysX rationale for kinematic CCTs: "the tunneling effect itself : if the character goes too fast it might tunnel through a wall"; "a rigid body is typically controlled with impulses or forces. It is usually not possible to move it directly to its final position"; friction is contradictory (infinite on ramps, none when moving); "even when the restitution is exactly zero, a physics engine can nonetheless make the CCTs bounce a bit"; "characters must often stick to the ground, no matter what the physical behavior should be"; "a typical character is always standing up and never rotating. However physics engines often have poor support for that sort of constraints." The PhysX CCT is "the 'collide and slide' algorithm" "tweaked for more than a decade", with `contactOffset` (skin), `stepOffset` (auto-step), `slopeLimit`, an up vector that "can be modified each frame" (spherical worlds), and pushing of dynamic actors done in game code through `PxUserControllerHitReport::onShapeHit()` "to apply artificial forces to surrounding dynamic objects" — [PhysX 5.1 documentation, Character Controllers, NVIDIA](https://nvidia-omniverse.github.io/PhysX/physx/5.1.0/docs/CharacterControllers.html)
- Jolt `Character`: "It uses a single rigid body, usually with a capsule shape to simulate movement and collision for the character. The character is a keyframed object, the application controls it by setting the velocity." Defaults: `mMass 80.0f`, `mFriction 0.2f`, `mGravityFactor 1.0f`, `mAllowedDOFs = TranslationX | TranslationY | TranslationZ`; `PostSimulation` "Needs to be called after every PhysicsSystem::Update" — [JoltPhysics Character.h, Jorrit Rouwe](https://raw.githubusercontent.com/jrouwe/JoltPhysics/master/Jolt/Physics/Character/Character.h)
- Jolt docs: `Character` "is generally unsuitable for player control since players typically need non-physical behaviors"; `CharacterVirtual` is "implemented purely through collision detection queries", supports sliding along walls, elevators/moving platforms, steep-slope (funnel) handling, stair stepping and ground sticking via `ExtendedUpdate`, custom up axes; its cost is update-order artifacts (may "briefly hover above descending elevators"); it "doesn't naturally push other bodies" but `CharacterVirtualSettings::mInnerBodyShape` adds an inner rigid body that follows the character so sensors and collision tests can see it — [Jolt Physics documentation](https://jrouwe.github.io/JoltPhysics/index.html)
- `CharacterVirtualSettings` defaults: `mMass 70.0f` ("Used to push down objects with gravity when the character is standing on top"), `mMaxStrength 100.0f` ("Maximum force with which the character can push other bodies (N)"), `mPredictiveContactDistance 0.1f`, `mCharacterPadding 0.02f`, `mPenetrationRecoverySpeed 1.0f`, `mMaxCollisionIterations 5`, `mMaxConstraintIterations 15`, `mCollisionTolerance 1.0e-3f`, `mHitReductionCosMaxAngle 0.999f`, `mBackFaceMode CollideWithBackFaces`. `ExtendedUpdateSettings`: `mStickToFloorStepDown (0,-0.5,0)`, `mWalkStairsStepUp (0,0.4,0)`, `mWalkStairsMinStepForward 0.02f`, `mWalkStairsStepForwardTest 0.15f`, `mWalkStairsCosAngleForwardContact cos(75 deg)`. `WalkStairs` casts "up, forward and down again to try to find a valid position"; `StickToFloor` does "an additional collision check downwards" — [JoltPhysics CharacterVirtual.h](https://raw.githubusercontent.com/jrouwe/JoltPhysics/master/Jolt/Physics/Character/CharacterVirtual.h)
- Godot: RigidBody: "You do not control a RigidBody2D directly, but instead you apply forces to it (gravity, impulses, etc.) and the physics engine calculates the resulting movement"; CharacterBody: "A body that provides collision detection, but no physics. All movement and collision response must be implemented in code."; physics changes to a RigidBody should go through `_integrate_forces()` — [Godot docs, Physics introduction](https://docs.godotengine.org/en/stable/tutorials/physics/physics_introduction.html); "Character bodies detect collisions with other bodies when moving, but are not affected by engine physics properties, like gravity or friction." — [Godot docs, Using CharacterBody2D/3D](https://docs.godotengine.org/en/stable/tutorials/physics/using_character_body_2d.html)
- Godot + Jolt specifics: "When using Jolt, a RigidBody3D frozen with FREEZE_MODE_KINEMATIC will by default not report contacts from collisions with other static/kinematic bodies, for performance reasons"; opt in via `Physics > Jolt Physics 3D > Simulation > Generate All Kinematic Contacts`; contact impulses from `get_contact_impulse()` "are estimated ahead of time" and only accurate when the two bodies touch nothing else; there is a `Use Enhanced Internal Edge Removal` setting — [Godot docs, Using Jolt Physics](https://docs.godotengine.org/en/stable/tutorials/physics/using_jolt_physics.html)
- Rigid-body alternative used in shipping games: Boneworks is a "pure simulation where there isn't something introducing an infinite force"; jumping is "your feet physically thrust down to propel yourself up"; player mass 82 kg (Laatsch) — [Game Developer](https://www.gamedeveloper.com/design/how-classical-game-mechanics-and-physics-converge-in-vr-hit-i-boneworks-i-)
- The "floating capsule" rigid-body controller pattern: an open-source Unity controller states it is "based on the floating capsule approach devised by Toyful Games for Very Very Valet", explained in Toyful's development video "with snippets of code, though incomplete in places" — [joebinns/stylised-character-controller README](https://github.com/joebinns/stylised-character-controller). (The controller source itself could not be fetched: raw path guesses returned 404 and the GitHub API is scoped to another repo in this session.)

### Inferences
- For the user's requirements (real impacts, procedural physics animation, momentum as the fun) the sensible split, supported by the Jolt docs, is: drive the player with `CharacterVirtual`-style kinematic movement (Godot `CharacterBody3D` under Jolt) for control and ground handling, and give it an inner rigid body (Jolt's `mInnerBodyShape`, 70 kg default) so walls, props and impact queries see a real body. Conversely, if the design wants "sprinting into a wall can kill you", the controller must read the pre-collision velocity and contact normal itself, since Jolt's kinematic contacts are estimated and off by default (`Generate All Kinematic Contacts`).
- Jolt's own defaults are already the "step handling" answer: 0.4 m step-up, 0.5 m stick-to-floor step-down, 75-degree forward-contact cone, 2 cm padding, 10 cm predictive contact. These are comparable to the 18-unit (0.46 m at 1 inch/unit) step size of Quake/Source.
- The floating-capsule (Very Very Valet) approach is the standard way to make a dynamic body feel like a kinematic one: a downward ray with a spring-damper "ride height" force, an upright torque spring, and a velocity-matching force (goal velocity minus current, scaled by acceleration, clamped by a max force). No primary GDC talk on it was located; treat the Toyful video as the reference.
- PhysX's list of rigid-body failure modes doubles as a checklist of what a physics-body controller must fake: infinite static friction when standing, zero friction when moving, no bounce, ground snap on stairs/slopes, locked rotation, and a speed cap or CCD to prevent tunneling.

### Gaps
- No GDC Vault talk specifically on physics-based (rigid-body) player controllers was located (search budget exhausted before this could be pursued); Bungie/Insomniac talks were not checked.
- Toyful Games' Very Very Valet controller video and the joebinns source code were not viewable, so no exact spring/damper constants are recorded.
- Jolt's `CharacterBaseSettings::mMaxSlopeAngle` default was not captured (the header fetch omitted it).

## Key question 4: Fall damage and impact damage rules actually used in games

### Takeaway
Two reproducible models dominate: speed-based (Half-Life/Source: damage grows linearly from a safe landing speed to a fatal one, `damage = (v_fall - v_safe) * 100/(v_fatal - v_safe)`, safe about 20 ft, fatal about 60 ft) and distance-based (Minecraft: `max(0, floor((fallDistance - 3) * multiplier))` HP, 23.5 blocks kills). Quake III uses a squared-speed "delta" with three thresholds (short/5 HP/10 HP) and, notably, doubles the delta if you land crouched. The only documented horizontal-impact rule found in a shipped game is Minecraft's elytra: `damage = 10 * (change in horizontal velocity) - 3`, applied for vertical surfaces only. Superhero games (Prototype, Apex, Titanfall-style) drop fall damage entirely or replace it with a "landing shock" slow.

### Cited Findings
- Half-Life 1: `PLAYER_FATAL_FALL_SPEED 1024 // approx 60 feet`; `PLAYER_MAX_SAFE_FALL_SPEED 580 // approx 20 feet`; `DAMAGE_FOR_FALL_SPEED (float) 100 / ( PLAYER_FATAL_FALL_SPEED - PLAYER_MAX_SAFE_FALL_SPEED ) // damage per unit per second.`; `PLAYER_MIN_BOUNCE_SPEED 200`; `PLAYER_FALL_PUNCH_THRESHHOLD (float)350 // won't punch player's screen/make scrape noise unless player falling at least this fast.` — [Half-Life SDK dlls/player.h](https://raw.githubusercontent.com/ValveSoftware/halflife/master/dlls/player.h). `PM_CheckFalling`: sound at full volume above safe speed, 0.85 above half safe speed, silent below `PLAYER_MIN_BOUNCE_SPEED`; view roll punch `punchangle[2] = flFallVelocity * 0.013` capped at 8 — [pm_shared.c](https://raw.githubusercontent.com/ValveSoftware/halflife/master/pm_shared/pm_shared.c)
- Half-Life 2 / Source SDK 2013: `PLAYER_FATAL_FALL_SPEED 922.5f // approx 60 feet sqrt( 2 * gravity * 60 * 12 )`; `PLAYER_MAX_SAFE_FALL_SPEED 526.5f // approx 20 feet sqrt( 2 * gravity * 20 * 12 )`; `PLAYER_LAND_ON_FLOATING_OBJECT 173 // Can fall another 173 in/sec without getting hurt`; `PLAYER_MIN_BOUNCE_SPEED 173`; `PLAYER_FALL_PUNCH_THRESHOLD 303.0f // ... at least a 76" fall (sqrt( 2 * g * 76))`; `DAMAGE_FOR_FALL_SPEED 100.0f / ( PLAYER_FATAL_FALL_SPEED - PLAYER_MAX_SAFE_FALL_SPEED )` — [Source SDK 2013 shareddefs.h](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/game/shared/shareddefs.h)
- Source damage formula (single player): `pPlayer->m_Local.m_flFallVelocity -= PLAYER_MAX_SAFE_FALL_SPEED; return pPlayer->m_Local.m_flFallVelocity * DAMAGE_FOR_FALL_SPEED;` with comment "subtract off the speed at which a player is allowed to fall without being hurt, so damage will be based on speed beyond that, not the entire fall" — [singleplay_gamerules.cpp](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/game/shared/singleplay_gamerules.cpp). - Prototype (Radical, 2009): "Falls cause no damage to the player even from the greatest heights." and "Falling height also factors into several of Alex's melee attacks." — [Prototype (video game), Wikipedia](https://en.wikipedia.org/wiki/Prototype_(video_game))
- Saints Row IV: superpowers "greatly increase their jump height and running speed, such that the player can hop over buildings and outrun vehicles" — [Saints Row IV, Wikipedia](https://en.wikipedia.org/wiki/Saints_Row_IV) (no fall-damage statement found)

### Inferences
- Source's model in SI units (using the 1 unit = 1 inch relation above): safe landing speed 526.5 u/s = 13.4 m/s, fatal 922.5 u/s = 23.4 m/s, damage slope 100/396 = 0.2525 HP per u/s = 9.9 HP per m/s. The comments' "20 ft" and "60 ft" are 6.1 m and 18.3 m, which under real gravity give 10.9 m/s and 18.9 m/s; Valve's numbers are computed with the game's own gravity (600 u/s^2 = 15.2 m/s^2), so if the user's game uses 9.81 m/s^2, the height-based intent (safe 6 m, fatal 18 m) is the thing to copy, not the speeds.
- Quake III thresholds converted: `delta = v^2 * 1e-4` so short landing at v > 264.6 u/s (a 43.8-unit drop at g = 800, i.e. just below the 45.6-unit jump height, so ordinary jumps make a footstep, not a "short fall"), 5 HP at v > 632.5 u/s (250-unit drop), 10 HP at v > 774.6 u/s (375-unit drop). Because the delta doubles when ducked, Q3 treats crouching on landing as worse; Halo and Mirror's Edge treat it as better. Both are choices the user must make explicitly.
- Q3's quadratic solve is worth copying for a physics build: it recovers the true impact speed even though the collision happened partway through the fixed step, so damage does not depend on tick phase.
- Minecraft's distance model with real gravity: 3 blocks = 7.7 m/s safe, 23.5 blocks = 21.5 m/s fatal — remarkably close to Source's 20 ft / 60 ft intent (both are roughly "you die at about 3 times the safe height"). A shared rule of thumb for "realistic" tuning: safe about 6 m (11 m/s), fatal about 18-24 m (19-21 m/s), linear in between.
- Elytra as a wall-impact template: `damage = 10 * dv_h - 3` with `dv_h` in blocks/tick (20 ticks/s) means no damage below 0.3 blocks/tick (6 m/s), 13.75 HP for a full stop from rocket speed (1.675 blocks/tick, 33.5 m/s), and death from 20 HP at 2.3 blocks/tick (46 m/s). Applying the same "change in horizontal velocity" rule to a sprinting human (Apex sprint 7.59 m/s) yields ~0.8 HP, i.e. harmless, which matches the user's plan that wall impacts only become lethal once superhuman speeds are reached; the constant in front of `dv` is the knob.
- Source already implements the "relative velocity" refinement (subtracting a descending platform's velocity, subtracting 173 for floating objects) that a physics-based game gets for free from a contact's relative normal velocity: `damage = k * max(0, |v_rel . n| - v_safe)` generalises Source's vertical-only formula to any surface normal, which is exactly the wall case.

### Gaps
- No shipped game other than Minecraft (elytra) was found with a documented formula for damage from running/flying into a wall; nothing was verified for Titanfall, Human: Fall Flat, Sonic, Just Cause (wingsuit), GTA, Spider-Man, Crackdown or Saints Row IV because their wikis were blocked and search was exhausted. Crackdown's Wikipedia article does not mention fall damage at all.
- Halo 3 and later: Halopedia's reduction page only covers CE and Halo 2; whether later games removed fall damage entirely was not confirmed.
- Dying Light's fall-damage thresholds (which heights hurt, which kill) are not in any opened source.
- Mirror's Edge damage per landing type (heavy landing HP loss) is not documented in opened sources.
- GTA IV/V fall damage rules: only that GTA IV uses NaturalMotion Euphoria for ragdolls (Wikipedia); no damage numbers.

## Key question 5: Landing rolls and recovery

### Takeaway
Every parkour game found gates the roll on an input pressed before impact and pays out in preserved speed, not just saved health: Mirror's Edge (crouch pressed roughly 10 ft above the ground, per player guides; DICE's own slides call them "skill rolls" under "layered landing animations"), Dying Light (Forward Roll skill, crouch before landing, window open while airborne, lethal heights still kill), Assassin's Creed (hold parkour button in older games; dodge-button roll in Shadows with an upgrade to fully cancel damage). Titanfall/Apex instead use no damage plus a "landing shock" slow, and Celeste's forgiveness rules (0.1 s jump grace, jump buffering, corner correction) give the timing-window design pattern.

### Cited Findings
- Mirror's Edge (DICE GDC slides): "Layered landing animations, Heavy landings / skill rolls" — [SlideServe transcript](https://www.slideserve.com/miron/creating-first-person-movement-for-mirror-s-edge-powerpoint-ppt-presentation). Player guide: "press crouch when you're around 10 feet from the ground. That is about the distance you'll need to make the roll register to not take fall damage." — [Steam Community guide (secondary)](https://steamcommunity.com/sharedfiles/filedetails?id=658340379). Analysis: "if you press the crouch button before landing from a higher height, you'll roll when you hit the ground, which means you have a little speed on landing, but don't lose all your speed from a heavy landing"; air kick downgrades a heavy landing to a light one — [CritPoints](https://critpoints.net/2020/10/31/mirrors-edge-review/)
- Dying Light Forward Roll (Fandom wiki, blocked; text from search snippet): "allows you to survive falls of great heights by pressing [CROUCH] before landing. The timing window is open as long as you are airborne"; "Falls from lethal heights (such as the tops of normal sized buildings) will still kill you regardless of attempting to roll" — [Forward Roll, Dying Light Wiki (snippet)](https://dyinglight.fandom.com/wiki/Forward_Roll). Community note (Dying Light 2 forum snippet): the roll does not work on a rebound crouch key, and there is a minimum height before an active landing can trigger — [Steam discussions (snippet)](https://steamcommunity.com/app/534380/discussions/0/3186862565356058543/)
- Assassin's Creed: "hold the climb up/parkour button while landing a jump to remove or reduce fall damage" (earlier games); Shadows: roll "by pressing the dodge button when they land, which initially only negates some fall damage, but upgrading the skill to Ninja Fall will cancel out all fall damage" — [GameRant (snippet)](https://gamerant.com/assassins-creed-ac-shadows-fall-damage/)
- Halo CE/2: "If a player manages to crouch just before impact with the ground" shields "will take little or no damage" — [Halopedia](https://www.halopedia.org/Fall_damage_reduction)
- Apex: landing shock "drastically slowing the player's movement speed" instead of damage — [Apex Legends Wiki](https://apexlegends.wiki.gg/wiki/Movement)
- Celeste timing windows (code): `JumpGraceTime = 0.1f` (coyote time), `VarJumpTime = .2f` (variable jump hold), `CeilingVarJumpGrace = .05f`, `HalfGravThreshold = 40f`, `WallJumpCheckDist = 3`, `DashTime = .15f`, `DashCooldown = .2f`, `DuckFriction = 500f`, `DodgeSlideSpeedMult = 1.2f` — [Celeste Player.cs](https://raw.githubusercontent.com/NoelFB/Celeste/master/Source/Player/Player.cs). ### Inferences
- The two roll-input schemes are "press within a window before impact" (Mirror's Edge: about 10 ft, i.e. about 0.4-0.5 s of fall at real gravity from that height) and "arm it any time while airborne" (Dying Light 1's Forward Roll). The second is essentially jump-buffering applied to landing; Celeste's `JumpGraceTime = 0.1 s` and its buffered jump are the same primitives, so a 0.1-0.2 s pre-landing buffer plus an "armed while airborne" option covers both shipped behaviours.
- Payout design: in every case the roll converts vertical speed into forward speed rather than deleting it (CritPoints: "a little speed on landing"), and no shipped game lets a roll cancel a lethal fall (Dying Light: building-height falls still kill). For a gated-powers game this suggests the roll should shift the safe/fatal thresholds by a fixed amount (Source-style: subtract a "roll allowance" from `fallVelocity` the way `PLAYER_LAND_ON_FLOATING_OBJECT` subtracts 173 u/s) rather than zero the damage.
- Dying Light's deliberately delayed parkour button and Titanfall's pre-wall-run camera tilt are both "make the commitment legible" fixes; a physics roll should telegraph (camera dip, hand reach) before the impact frame.

### Gaps
- Exact roll windows in seconds or the speed retained after a roll were not published for Mirror's Edge, Dying Light or Assassin's Creed; only player estimates ("10 feet", "1-2 seconds").
- Zelda (BotW/TotK) landing behaviour and stamina interplay: no source could be opened.

## Key question 6: What makes momentum fun (designer statements and analyses)

### Takeaway
Designers converge on three statements: momentum must be a reward you can lose (Channon: "the fuel that drives you through the game"), the controls must stay minimal and context-sensitive so the skill lives in combinations rather than button count (Channon, Haggerty), and the game must be generous about intent (Thorson's forgiveness mechanics, Kulon's jump assists and delayed button, Titanfall's camera tilt and not falling off wall tops). Where realism conflicted with fun, DICE broke realism (instant stop after sprint) and Respawn shipped things they initially thought were "stupid" because playtesters loved them.

### Cited Findings
- Nick Channon (DICE): "that flow, and that momentum, that's what it's all about; it's so rewarding when you do it."; "it's all about keeping the momentum, which is like the fuel that drives you through the game"; "we wanted to create a game that was all about movement."; "we spent a lot of time in white box, that we really proved out what we were doing, very early." — [Game Developer](https://www.gamedeveloper.com/design/the-philosophy-of-faith-a-mirror-s-edge-interview)
- DICE broke realism for feel: stopping instantly after a sprint "because the development team felt that keeping the inertia would make the gameplay irritating" — [Wikipedia, citing IGN 2008](https://en.wikipedia.org/wiki/Mirror%27s_Edge)
- Respawn: Rayme Vinson (senior software engineer): "Just in the moment we had those tools, someone tried a thing, and oh, shit! That works."; Haggerty on the slide being loved once tried; on wall-running needing a reason to exist ("Why would you wall-run when you can just run around?") and needing trust — [Game Developer](https://www.gamedeveloper.com/design/designer-interview-getting-i-titanfall-i-s-controls-just-right)
- Titanfall 2 removed a punishment (no longer falling off near wall tops) and made combat animations interruptible by movement for "greater control and freedom" (Alavi) — [Wikipedia](https://en.wikipedia.org/wiki/Titanfall_2)
- Maddy Thorson (Celeste): "A short thread on a few Celeste game-feel things :) I don't think we invented any of these." followed by the ten forgiveness mechanics (coyote time, jump buffering, half-gravity apex, corner corrections, lift boost, 2- and 5-pixel wall-jump leniency, stamina refund on converted wall jumps) — [ThreadReader](https://threadreaderapp.com/thread/1238338574220546049.html); the mechanics' common pattern is that they widen timing and position windows so the game reads the player's intent — [Gigazine](https://gigazine.net/gsc_news/en/20200317-celeste-action-feel-things/)
- Celeste's tuning numbers that define its feel: `MaxRun = 90f; RunAccel = 1000f; RunReduce = 400f; AirMult = .65f; JumpSpeed = -105f; JumpHBoost = 40f; VarJumpTime = .2f; Gravity = 900f; MaxFall = 160f; FastMaxFall = 240f; DashSpeed = 240f; EndDashSpeed = 160f; DashTime = .15f` (pixels and seconds) — [Player.cs](https://raw.githubusercontent.com/NoelFB/Celeste/master/Source/Player/Player.cs)
- Kulon (Techland): "A simple jump in a first-person perspective game is much harder than people would think"; three jump-assist algorithms — [GDC Q&A](https://gdconf.com/news/speaker-qa-bartosz-kulon-explains-turning-nba-dreams-game-dev-expertise); letting the player look around during locked animations fixed the "passenger" feeling — [Game Developer](https://www.gamedeveloper.com/design/game-design-deep-dive-i-dying-light-i-s-natural-movement-system); motion sickness required "a multitude of tests and commissioned an external study", adjusting "motion blur levels, the movement of the camera and the positioning of the aiming reticle" — [same](https://www.gamedeveloper.com/design/game-design-deep-dive-i-dying-light-i-s-natural-movement-system)
- Ben Esposito (Neon White): "if everything was intentional on our end, it almost wouldn't be as fun."; players discovered parrying their own grenade for speed: "I had never thought of doing it to my own projectile because that's absurd." — [TheGamer](https://www.thegamer.com/neon-white-ben-esposito-interview/)
- Ghostrunner 2: "Players wanted us to expand the core combat and movement mechanics, and that's what we focused on." (Ratusznik) — [Game Developer](https://www.gamedeveloper.com/design/ghostrunner-2-deep-dive); Ghostrunner 1 keeps failure cheap: "never lose more than 30 seconds' worth of progress" — [PCGamesN](https://www.pcgamesn.com/ghostrunner/review)
- Laatsch (Boneworks) on grounding: the 82 kg player weight "helps ground the design"; jumps as an "equal opposite reaction" — [Game Developer](https://www.gamedeveloper.com/design/how-classical-game-mechanics-and-physics-converge-in-vr-hit-i-boneworks-i-)
- Grow Home: "you get a real sense of vertigo and you're acutely aware of the long drop below you." (Young) — [Ubisoft News](https://news.ubisoft.com/en-us/article/7fDmgKCCwWJQtyoVoOvvGM/get-ready-to-grow-home)
- Jusant: climbing is "about managing the combination of all these mechanics while managing your stamina", "almost like a dance" — [DON'T NOD](https://dont-nod.com/en/scaling-new-heights-learn-more-about-jusants-innovative-climbing-system/)

### Inferences
- The Celeste constants translate directly to 3D tuning ratios: ground acceleration about 11x max speed per second (`1000/90`, i.e. 0.09 s to top speed, the same order as Quake's 0.1 s), deceleration 4.4x (`400/90`), air control 65% of ground, jump horizontal boost about 44% of run speed, a 0.2 s variable-jump window and 0.1 s coyote time. Quake and Celeste agree that "fast to accelerate, slower to decelerate, very fast to stop below a threshold" feels responsive; Mirror's Edge's slow 8 s build is the exception that made momentum a visible reward.
- Every studio quoted decoupled "physically realistic" from "feels good" at a specific point: DICE at stopping, Respawn at wall-run speed gain and not falling off wall tops, Thorson at input timing, Kulon at button latency. For the user's realism goal, the safest place to spend "unrealism" is in input interpretation (buffers, coyote time, assists) rather than in the simulation, which matches Boneworks' "pure simulation" body plus assisted intent.
- The consequence gates the user wants (fall tolerance after high jump, impact tolerance after sprint) have precedent as "skills": Dying Light's Forward Roll and Assassin's Creed Shadows' Ninja Fall are unlockable damage-cancelers, and Ghostrunner 2 added block/stamina as accessibility valves.
